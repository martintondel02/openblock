## 1. Purpose and scope

This chapter defines how OpenBlock knows that it works and that it is still
fast: the test pyramid, the harnesses that make each layer cheap to write, the
benchmark machinery, and the CI policy that turns a budget into a gate.

The division of labour with [chapter 25](25-performance-budgets.md) is strict.
**Chapter 25 owns the numbers** — frame, tick, memory, IO and network budgets.
**This chapter owns the machinery** that measures them, the tolerance policy and
the reporting. A benchmark without a budget is a graph nobody reads; a budget
without a benchmark is an assertion. `PERF-TEST-*` here budgets the *test system
itself* (suite duration, fixture size, flake rate); it never restates a
`PERF-RENDER-*`, `PERF-WORLD-*` or `PERF-NET-*` number.

In scope: layer definitions and where each runs (§3.1); tooling and the harness
(§3.2–§3.5); replay, determinism, golden worlds, golden images (§3.6–§3.8); what
must be tested and how (§3.9); fuzzing (§3.10); benchmarks and performance CI
(§3.11–§3.12); soak and scale (§3.13); coverage (§3.14); debugging integration
(§3.15); traceability (§3.16); and the testing definition of done and release
checklist (§3.17).

Out of scope: the content of each subsystem's invariants, which belongs to its
own chapter and is only summarised in §3.9; release engineering and signing
([22](22-platforms-and-distribution.md)); the anti-cheat corpus specifics
([20 §7](20-security-and-anti-cheat.md#7-testing-strategy)).

One rule frames the chapter: **a test that cannot fail is documentation**. Every
layer below names the bug class it catches and the mechanism that makes it fail
loudly; anything else is a demo.

## 3. Design

### 3.1 The pyramid

| Layer | What it proves | Typical runtime | Tier | Tooling |
| --- | --- | --- | --- | --- |
| Unit | A function matches its contract | < 60 s total | PR | `nextest` |
| Property / model | An invariant holds for generated inputs; a state machine matches a model | ≤ 5 min | PR | `proptest` |
| Integration | Crates compose: world + sim + content + protocol | ≤ 5 min | PR | `nextest` + temp worlds |
| Scenario (end-to-end) | A scripted session produces the required events and outcomes | ≤ 10 min | PR subset, nightly full | headless host + scenario RON |
| Golden image | Pixels match with tolerance under a fixed scene | 3–8 min per scene | Nightly GPU | lavapipe + hardware box |
| Replay / determinism | Identical inputs produce an identical state hash | ≤ 10 min per platform | Nightly, 3 platforms | `xtask sim replay` |
| Network simulation | Behaviour under loss, jitter, reordering and migration | ≤ 5 min | PR subset, nightly 30 min | in-process `Transport` |
| Fuzz | No panic, no OOM, no hang on hostile input | 24 h campaigns | Nightly subset, release full | `cargo-fuzz` |
| Soak / scale | Time and population do not degrade the server | 2–24 h | Nightly (2 h), weekly (24 h) | bot swarm + metrics |
| Manual checklist | Hardware, IME, controller, accessibility, feel | 1–2 days | Per release | recorded checklist |

The pyramid is deliberately inverted at the top for cost reasons: the cheap
layers run on every push, and the expensive layers run on schedules with
artifacts that make failures reproducible. A layer does not exist unless a
developer can run it locally, or the tooling table (§3.2) names the local
approximation and the nightly owner.

### 3.2 Tooling

| Purpose | Tool | Invocation | Notes |
| --- | --- | --- | --- |
| Test runner | `cargo-nextest` | `cargo nextest run --workspace` | Per-test timeouts, retries disabled, JUnit output for CI |
| Snapshots | `insta` | `cargo insta test --review` | Snapshot files reviewed like code; no `--accept` in CI |
| Property tests | `proptest` | inline | Shrinking on by default; seeds printed for replay |
| Fuzzing | `cargo-fuzz` (libFuzzer) | `cargo +nightly fuzz run proto_decode` | Nightly toolchain only; corpora are versioned |
| Microbenchmarks | `criterion` | `cargo bench --bench world` | JSON output, change detection, p50/p95/p99 |
| Frame benchmarks | in-engine scene runner | `cargo xtask bench frame --scene flythrough` | Fixed camera path and input log, no vsync |
| Shader validation | `naga` | `cargo xtask check-shaders` | Parse + validate every stage, all backends' entry points |
| Dependency audit | `cargo-deny` | `cargo deny check` | Advisories, licences, sources, bans |
| Coverage | `cargo-llvm-cov` | `cargo xtask coverage` | Per-area report, uploaded as an artifact |
| Mutation | `cargo-mutants` | `cargo xtask mutants --area inventory` | Sampled subsets, never on the PR path |
| Compile cache | `sccache` | CI env | Optional; cold-cache parity job in §3.12 |
| Profiler capture | `tracing` spans → Chrome trace; RenderDoc / Metal tools for frames | `xtask profile` | Attached to failing bench jobs |
| Crash dumps | `ob_core` crash reports | automatic | Local-only, opt-in attachment |

No harness crate is added to the shipped graph: REQ-ARCH-001 fixes the crate
list. Harness code lives in `xtask` (developer-only, allowed to depend on
anything) and in the owning crate's `tests/`; `ob_server` exposes the same
`Host`, `HostConfig`, loopback transport and `HostHandle` it uses for single-player, so
the harness exercises production code rather than a mock ([DEC-003](../decisions.md)).

### 3.3 Headless harness and scenarios

A scenario is a versioned RON file that builds a world, starts a host, applies
inputs and asserts observable outcomes:

```ron
Scenario(
  id: "first_night",
  version: 3,
  world: (seed: 20261124, content: "base@1.0.0", generator: "overworld", edits: []),
  players: [(name: "bot", mode: Survival, at: [0.5, 70.0, 0.5])],
  steps: [
    Tick(at: 0, actions: ["sprint(false)", "look(0.0, 0.0)"]),
    Tick(at: 400, actions: ["break([2, 69, 0])",
                           "expect(inventory.contains(openblock:oak_log, 1))"]),
    Until(limit: 24000, predicate: "player.alive"),
  ],
  checks: [
    (when: AtTick(24000), expr: "player.health > 0"),
    (when: Always, expr: "tick_p99_ms < 35"),
    (when: Always, expr: "no_protocol_error"),
  ],
)
```

Assertions address named state through the same accessors as the debug overlay
(§3.15), so a failing scenario prints the values it compared. The runner is
`cargo xtask scenario run <id> --record-video <path>`; `--record-video` writes a
frame sequence off the critical path for bug reports, never a golden image.

Scenarios are recorded, not composed by hand, whenever a real session is the
source: `xtask scenario record` captures inputs and observations, then a human
prunes the assertions. This keeps the harness honest about what a player can
actually do, and it is the same mechanism as the replay log ([02 §3.10](02-engine-core.md#310-determinism-harness)).

### 3.4 Network simulator

The simulator plugs a deterministic `Transport` into the host and clients. Time
is virtual; per-packet `splitmix64(seed, packet_index)` decides drop, delay and
duplication, so a failing run is reproducible from the seed alone.

| Profile | One-way delay | Loss | Reorder | Duplication | Bandwidth |
| --- | --- | --- | --- | --- | --- |
| `lan` | 1 ms ± 0.2 | 0% | none | 0% | 1 Gbit/s |
| `broadband` | 25 ms jitter 5 | 0.1% | 1% | 0.01% | 50 Mbit/s |
| `mobile` | 60 ms jitter 25 | 2% | 3% | 0.1% | 5 Mbit/s |
| `lossy` | 150 ms jitter 50 | 5% | 5% | 1% | 2 Mbit/s |
| `blackhole` | — | 100% for 2 s windows | — | — | 0 |
| `join_storm` | 40 ms ± 10 | 0.5% | 2% | 0.05% | 100 Mbit/s shared |

PR scenarios use `broadband` and `lossy`; `blackhole` proves reconnection and
interest-set recovery; `join_storm` is a nightly scale test. The simulator also
faults the transport layer (close mid-stream, stall a stream, refuse a
datagram), because the highest-value protocol bugs live in partial failure.

### 3.5 Bots and scale

A bot is a headless client built from `ob_client`'s protocol and prediction code
compiled without presentation. Bots are scripted as state machines
(move, mine, build, fight, idle) and can be mutated by the cheat corpus
([20 §7.1](20-security-and-anti-cheat.md#71-cheat-bot-corpus)). The scale
harness starts up to 500 in one process on the reference VPS, reports per-bot
RTT and correction counts, and is the executor for the MS-15 capacity matrix.
Bot inputs are seeded, so a 50-bot run reproduces exactly when the server build
and seeds match; non-deterministic scheduling in the OS is absorbed by the
server's tick, not by the test.

### 3.6 Replay, determinism and state hashing

Determinism is a testable property because the simulation has no inputs beyond
its log ([02 §3.10](02-engine-core.md#310-determinism-harness)). The harness:

1. Replays an `OBIL` log and compares the 32-byte BLAKE3 state hash at every
   checkpoint (default every 20 ticks) with the recorded values.
2. Runs the same log on Linux x86_64, Windows x86_64 and macOS aarch64 in the
   nightly job, and on x86_64 and aarch64 Linux headless runners.
3. Fails with the first diverging tick, the subsystem hash table, and the log
   path, so the failure is a reproduction command rather than a mystery.
4. Registers a negative control: a deliberately unordered system must be caught,
   proving the harness detects divergence rather than merely agreeing with
   itself.

Seed corpus: a 500-seed PR subset of the worldgen corpus declared in
`tests/worldgen/corpus.toml` (the nightly 10,000-seed corpus is chapter 06's,
REQ-GEN-029), each seed generating a fixed 64-chunk set across three dimensions,
plus 50 input logs of 600 ticks (movement, mining, inventory, combat, redstone,
weather). Golden hashes live in `tests/corpus/hashes.blake3`, one line per case,
regenerated only by a reviewed `xtask hash-accept` whose PR carries the
`hash-version` label and touches no gameplay code.

### 3.7 Golden worlds, fixtures and test data

| Fixture class | Generated by | Size target | Used for |
| --- | --- | --- | --- |
| `worldgen/<seed>` | `xtask fixture gen worldgen --seed N --radius 2` | ≤ 256 KiB | Terrain, biome, structure determinism |
| `save/migrate/<version>` | Released builds, one per release | ≤ 8 MiB each | Migration and forward-compat tests |
| `save/torn/<profile>` | Fault injector | ≤ 8 MiB | Power-loss recovery |
| `lighting/<scene>` | Scripted edits on a flat world | ≤ 1 MiB | Differential lighting |
| `redstone/<circuit>` | Content-locked structures | ≤ 64 KiB | Update-order and timing goldens |
| `inventory/<case>` | Transaction replayer | ≤ 16 KiB | Conservation and duplication |
| `physics/<course>` | Block layout + input script | ≤ 64 KiB | Collision and raycast conformance |

The fixture manifest (`tests/fixtures.toml`) records id, generator command,
BLAKE3, size, purpose, owner and the requirement IDs it serves. CI regenerates
every fixture from its command and fails if the bytes differ — the
`save/migrate/*` class is the one exemption: it is recorded from the tagged
release and verified by hash only. That is how "golden" stays a claim about the
generator rather than about a binary blob someone once committed. Total repository test data is capped at 300 MiB
(PERF-TEST-005); anything larger is fetched from a content-addressed release
artifact or generated on demand.

### 3.8 GPU golden images

Golden images are a regression net for the renderer, not an art review. Each
image is `(scene, preset, resolution, adapter-class)` with a mask of rectangles
that are excluded from comparison: dynamic text, particles, TAA-jittered edges
and the debug overlay.

| Field | Value |
| --- | --- |
| Comparison | SSIM ≥ 0.99 and mean absolute error ≤ 2/255 over the unmasked area |
| Reference adapter | lavapipe in CI; hardware references stored per adapter class |
| Tolerances | Hardware runs allow ±1 LSB per channel; a driver update that breaks the gate opens a `golden-update` PR |
| Scenes | `flythrough`, `tnt`, `water`, `cave`, `megabuild` (03 §3.12) plus `shaderpack_sample` |
| Update process | Label `golden-update`, two reviewers, the before/after image pair in the PR description |
| Storage | PNG/AVIF in `tests/images/`, ≤ 30 MiB total, mask as a sidecar JSON |

A broken golden is triaged as a renderer bug first. Only after two reviewers
agree that the new output is intended may the reference change; the PR states
which pass changed and why, which is exactly the information a bisect cannot
recover later.

### 3.9 What must be tested, and how

| Area | Invariant or bug class | Technique | Tier |
| --- | --- | --- | --- |
| World storage | Palette round-trip, uniform fast path, light packed exactly, no index overflow at section edges | Property tests over random sections + hash round-trip | PR |
| Meshing | Greedy output is watertight, no interior faces, UV/tile correct per face, AO matches reference | Golden quad dumps vs a slow reference mesher; quad-count assertions | PR |
| Lighting | Incremental updates equal a full recompute; sky and coloured channels independent | Differential test against a reference flood fill after every edit batch | PR |
| Physics | No tunnelling at terminal velocity, step height, slab/stairs shapes, raycast hits the nearest face | Analytic conformance vectors + invariant fuzz ([02 §3.10](02-engine-core.md#310-determinism-harness)) | PR |
| Redstone | Update order, tick delays, documented connectivity rules, cross-region propagation | Golden circuits with expected event traces | PR subset, nightly full |
| Inventory | Counts conserved across every transaction, including death, disconnect, dimension change and container destruction | 100k randomised sequences in the network simulator ([11 §7](11-inventory-crafting-items.md#7-testing-strategy)) | Nightly |
| Worldgen | Bit-identical output across platforms and worker counts; no cascade, no orphan structure starts | 500-seed corpus, state hashes, structural assertions | Nightly |
| Persistence | Power loss loses at most the last cycle; migrations round-trip; quarantine never drops data | Fault injection, fixture migrations, 1,000 schedules | Nightly |
| Protocol | No panic or OOM on hostile input; version/content negotiation is actionable | Fuzz + negative fixtures + in-process loopback | PR subset, nightly full |
| Mod sandbox | Known escapes blocked, quotas enforced, trap leaves host alive, every host call tested | Escape corpus + per-function tests + trap injection | PR |
| UI | Every screen renders, navigates by keyboard, respects UI scale, never traps focus | Screenshot + navigation tests at 3 resolutions × 2 scales | PR subset, nightly full |
| Accessibility | Contrast, focus order, labels, remap conflicts, reduced motion | Automated checks + the [23 §3.17](23-accessibility-localization.md#317-the-accessibility-audit-checklist) audit with two external testers | Release |
| Parity | Every Tier-1/2 row has a test or a documented divergence | Generated manifest assertions | Weekly |
| Network feel | Corrections converge, no ghost blocks, inventory never desyncs under loss | Scenario + simulator profiles | PR |

The table is the index, not the specification: each row's owning chapter defines
the exact assertions. A row without an owner chapter is a planning bug.

### 3.10 Fuzzing

| Target | Input | Invariants |
| --- | --- | --- |
| `proto_decode` | Handshake, control, input frame, tick delta | No panic, no allocation above cap, typed error, connection close with reason |
| `chunk_blob` | Compressed chunk payloads | Declared length respected, no read past buffer, cap enforced before allocation |
| `region_file` | Headers, index entries, blobs | Checksums verified, quarantine on failure, no path outside the root |
| `pack_load` | RON/JSON manifests and assets | Schema errors are actionable; no code loaded; caps enforced |
| `mod_abi` | Module bytes and host-call sequences | Quotas enforced, trap contained, no host memory exposed |
| `chat_cmd` | UTF-8, control characters, command grammar | Bounded output, no panic in the parser, permission checked before parse |

Campaigns run with a 2 GiB RSS limit, a 10 s per-input timeout and a seed corpus
in `fuzz/corpus/<target>/`. A crash artifact is committed as a regression seed,
named with the issue number, and the target is re-run on the PR that fixes it.
The release gate is a 24 h campaign per target with no new crash
([MS-15](../plan/01-milestones.md) exit criterion); corpora are pruned only when
a seed no longer reaches new coverage, and the manifest records the pruning.

| `tick50` | headless | 50 players, entities, scheduled ticks | 600 ticks | tick p95/p99, validation share |

| `relight` | headless | 4,096 edits in one region | 200 ticks | propagation time, tick share |
| `redstone_stress` | headless | reference circuits: clocks, dust nets, repeaters, pistons, hoppers ([12 §7](12-redstone-and-logic.md#7-testing-strategy)) | 10 min | tick p50/p95/p99/max, update-order hash |
| `pack` | headless | pack validation and registry freeze | 100-pack corpus | validate ms/pack, load p95 |

The set above is the current one; chapter 25's budget manifest is authoritative
and may add a scene behind a new budget row. Scene names, seeds, camera paths,
input logs and content locks live in `perf/scenes.toml` and are hashed into
`scene_hash`; a rename is a new scene and needs a new baseline. A run is recorded in the `openblock.bench/1` JSON of
[25 §4.2](25-performance-budgets.md#42-bench-report) and compared with
[25 §4.3](25-performance-budgets.md#43-comparison-algorithm). Chapter 24 adds no
second report format and no second tolerance rule; instead, a per-milestone
summary is committed as `benchmarks/<milestone>.md`, run JSON is written to
`perf/reports/` and retained for ≥ 400 days ([REQ-PERF-013](25-performance-budgets.md)).

To add a benchmark: (1) define the scene in `perf/scenes.toml` with a fixed seed,
input log or camera path, and content lock; (2) add the budget row to
`perf/budgets.toml` — id, metric, percentile, scene, gate class
([25 §4.1](25-performance-budgets.md#41-budget-manifest)); (3) run it ten times on
the bench box to establish its noise floor; (4) regress the code artificially and
prove the gate fails; (5) record the baseline and announce it in the milestone
issue. Step 4 is not optional — an ungated benchmark is a dashboard.

### 3.12 Performance CI policy

| Tier | Contents | Runner | Wall-clock cap |
| --- | --- | --- | --- |
| PR | test tier; Gate-class scenes (chapter 25 §7 subset; lane packing open, §8); `pack`; microbench subset (`Warn`) | bench box, shared, parallel with tests | 8 min bench lane, 12 min tests |
| Nightly | full scene matrix, allocation tracking, two-run confirmation | bench box, exclusive | 45 min |
| Weekly | capacity matrix (vCPU × players × distance), container reference | reference VPS | 3 h |
| Release | everything, twice, on the release candidate | bench box + VPS | 6 h |

Gate classes, thresholds, the bootstrap confidence interval and the noise-floor
rule are
[25 §3.8](25-performance-budgets.md#38-enforcement-gates-and-the-change-process)
and are not repeated here. This chapter adds the operational rules that keep
those numbers meaningful:

- The first failure re-runs the same binary automatically; a gate blocks only
  after the second failure, the perf bot opens the bisect immediately and the
  author has two working days to fix or revert (25 §3.8).
- A bench whose result moves beyond its recorded floor with no code change is
  labelled `bench-flaky` and becomes `Warn` for at most seven days with a named
  owner and repair date; silent acceptance is not allowed.
- The bench lane never shares a runner with a soak or a fuzz campaign;
  contention is the commonest cause of a false regression.
- A box that cannot reproduce its own control workload within 1% is taken out of
  service rather than trusted.

Pipeline budget: PR CI wall time ≤ 25 min p95 excluding queue (PERF-TOOL-003),
split into ≤ 12 min of tests and ≤ 8 min of bench lane, leaving build and lint
headroom.

### 3.13 Soak and scale

| Test | Duration | Population | Assertions |
| --- | --- | --- | --- |
| `soak_2h` | 2 h, nightly | 50 bots | RSS slope ≤ 0.5%/h, no FD growth, tick rate ≥ 19.5/s, no protocol error |
| `soak_24h` | 24 h, weekly and pre-release | 50 bots + join/leave churn | RSS slope ≈ 0, save growth bounded, zero crashes, zero corruption |
| `join_storm` | until stable | 50 simultaneous joins | join p95 ≤ 30 s on 10 Mbit/s, tick p99 ≤ 35 ms during joins |
| `churn` | 4 h | 500 joins/leaves | interest sets freed, no handle leak, entity count bounded |
| `scale_matrix` | 30 min per cell | 10/25/50/100 bots × 128/256/512 blocks | p99 tick and RSS recorded in the matrix |

The soak driver records the metric series, not just the endpoints, because a
leak that starts at hour 18 is invisible in a start/end comparison. A failed
soak keeps the world directory and the last 10 minutes of logs for analysis.

### 3.14 Coverage

Coverage is a diagnostic, not a scoreboard. It is reported per area and never
enforced globally, because a single number lets a renderer with golden images
and a parser with fuzzing both look "under-covered".

| Area | Target | Rationale |
| --- | --- | --- |
| `ob_world`, `ob_sim` | ≥ 85% line, ≥ 75% branch | State-machine bugs hide in branches |
| `ob_protocol` decoder | ≥ 90% branch | Every arm is an attacker's entry point |
| `ob_modding` host functions | 100% called at least once | Untested host calls are unshipped API |
| `ob_content` validation | ≥ 90% line in the validation module | Validation is the security boundary |
| `ob_render` | No line target | Golden images and validation layers are the gate |
| Workspace reported | ≥ 70% | Reporting only; a drop is a discussion, not a build failure |

Exclusions are explicit (`llvm-cov` ignore attributes with a reason) and reviewed
when they change. A coverage drop on a PR that adds logic is flagged in review,
but a green coverage number never excuses a missing golden or a disabled test.

### 3.15 Debugging integration

- **Replay from a bug report**: `xtask sim replay --log case.obil --break-on-divergence`
  stops at the first hash mismatch and prints the subsystem table.
- **Scenario stepping**: `xtask scenario run --step` pauses per tick with the
  overlay available; `--capture` writes the trace and a profiler capture.
- **Frame capture**: the failing bench job attaches the Chrome trace and, for
  renderer failures, the RenderDoc/Metal capture path is printed in the log.
- **Crash dumps**: local, opt-in, with the §4.5 fields of [01](01-technical-architecture.md#45-crash-report-contents);
  the test job never uploads a dump containing player data.
- **State inspection**: the same accessors used by the debug overlay are
  available to scenarios, so an assertion and a human see the same values.

### 3.16 Traceability and naming

`tests/traceability.toml` is the bridge between prose and tests:

```toml
[[req]]
id = "REQ-SAVE-003"
kind = "auto"
test = "req_save_003_crc_bitflip"
owner = "MS-13"

[[req]]
id = "REQ-TEST-022"
kind = "manual"
check = "reports/a11y-audit-<release>.md"
owner = "MS-14"
reason = "requires a human observer and OS assistive technology"
```

`cargo xtask check-trace` parses the requirement tables of every chapter, checks
that each ID appears exactly once, that automated entries point at a test that
currently exists and passes in the PR tier, and that manual entries name a
recorded check with an owner. A requirement may be `manual` only with a reason;
"hard to test" is not a reason, and more than 5% manual in any chapter is
reviewed by the area owner. Test names follow REQ-TEST-007 so `nextest` output is
already a requirement report.

### 3.17 Definition of done and release checklist

Testing is done for a change when: the owning requirement has a test that fails
without the change; the test runs in the PR tier or has a nightly owner; a
regression test exists for every fixed bug; benchmarks for touched hot paths
were run and recorded; and no test was disabled, skipped or quarantined without
an issue and a date.

The release checklist, executed on the release branch:

1. PR and nightly tiers green on Linux, Windows and macOS for the exact tag.
2. Cross-platform replay corpus identical; hash version unchanged or reviewed.
3. Full bench set within budgets, twice, on the bench box; results committed.
4. 24 h soak and capacity matrix pass; numbers match the published matrix.
5. Fuzz campaigns 24 h per target with no new crash; corpora committed.
6. Fixture regeneration reproduces every generated golden byte-for-byte; recorded migration fixtures match their hashes.
7. Save migrations from every released version pass; a fresh save opens.
8. Accessibility audit and UI screenshot suite recorded.
9. Security: penetration checklist and red-team findings closed
   ([20 §7.3](20-security-and-anti-cheat.md#73-penetration-test-checklist-and-red-team)).
10. Traceability lint clean; no `#[ignore]` on a shipped path, and every quarantined test has an issue, an owner and an expiry.

## 4. Data structures and formats

```rust
pub struct Scenario {
    pub id: String,              // stable, kebab-case
    pub version: u16,
    pub world: WorldSpec,        // seed, content lock, generator, edit script
    pub players: Vec<PlayerSpec>,
    pub steps: Vec<Step>,
    pub checks: Vec<Assertion>,
}

pub enum Step {
    Tick { at: Tick, actions: Vec<Action> },
    Until { limit: Tick, predicate: Predicate },
}

pub struct Assertion {
    pub when: When,              // Always | AtTick(Tick) | Never
    pub expr: Expr,             // parsed once, type-checked against the accessor table
    pub message: Option<String>,
}

pub struct BenchScene {
    pub id: SceneId,             // must exist in perf/scenes.toml and perf/budgets.toml
    pub kind: SceneKind,         // Frame | Headless
    pub seed: u64,
    pub content: ContentLock,    // pack hashes + data version
    pub input_log: Option<String>,   // OBIL path, content-addressed
    pub camera_path: Option<String>,
    pub duration: Duration,
    pub warmup: Duration,        // 10 s for frame scenes
    pub scene_hash: [u8; 32],    // BLAKE3 over the resolved descriptor
}

pub struct FixtureEntry {
    pub id: String,
    pub generator: String,       // exact xtask command
    pub blake3: [u8; 32],
    pub bytes: u64,
    pub purpose: String,
    pub requirements: Vec<String>,
}
```

Scenario and manifest files are data, not code: no arbitrary script evaluation,
a closed accessor namespace, and a version field so an old scenario fails with
"scenario version 2 is no longer supported" rather than silently asserting
nothing. A `BenchScene` never carries a budget or a threshold: those are read from
`perf/budgets.toml` by the runner, so a scene cannot quietly gate itself. The run
report, percentile calculation and comparison live in
[chapter 25 §4.2–§4.3](25-performance-budgets.md#42-bench-report) and are used as
specified, never reimplemented here.

## 6. Failure modes and edge cases

- **Flaky test.** Quarantine on first repeat failure, label `test-flaky`, keep it
  running in a non-blocking lane, and fix or delete within 10 days. Retries are
  forbidden because they convert a bug into a statistic (REQ-TEST-004).
- **Slow CI.** If the PR tier exceeds 12 min, move the slowest long-tail tests to
  nightly by *tier change with an owner*, never by deletion or `--skip`.
- **Golden-image brittleness.** A font, driver or particle change churns images.
  Masks cover dynamic regions, references are adapter-classed, and an update PR
  needs two reviewers, so churn is visible instead of routinely accepted.
- **Benchmark noise.** The box drifts with thermals or a co-tenant. The control
  workload catches it; a failed control invalidates the run instead of failing
  the PR.
- **Untested mod path.** A host function without a test is a public API with
  unknown behaviour; REQ-TEST-020 makes it a build failure, and the sandbox
  corpus covers escape paths rather than only happy paths.
- **Fixture rot.** A generator change silently rewrites goldens. Regeneration
  runs in CI and a byte difference in a PR without an intentional change is a
  failure, not a cache miss (recorded migration fixtures are verified by hash,
  not regenerated).
- **Hash churn.** A single gameplay change re-baselines every replay. Hashes are
  versioned and one reviewed PR regenerates them; the label makes the blast
  radius obvious during review.
- **Order-dependent tests.** A shared port or temp directory turns a green suite
  red when `nextest` schedules differently; per-test sandboxes (REQ-TEST-036)
  remove the class.
- **Coverage gaming.** Tests that call code without asserting inflate the number.
  Mutation testing on critical modules is the counterweight (REQ-TEST-026).
- **Simulator that cannot fail.** A transport simulator that drops nothing proves
  nothing; its self-test asserts each profile actually produces the loss,
  reordering and duplication it advertises.
- **GPU-free CI blind spot.** CI without a real GPU misses driver-specific
  validation errors; a nightly hardware job and a lavapipe smoke test cover the
  two classes.

## 7. Testing the tests

| Check | What it proves |
| --- | --- |
| Negative control for determinism | The harness catches unordered iteration (02 §3.10) |
| Negative control for each AC rule | A disabled validator is caught by the cheat corpus ([20](20-security-and-anti-cheat.md)) |
| Mutation sampling | Inventory, lighting, protocol and save tests fail when the code is mutated |
| Benchmark canary | A deliberately regressed build fails the gate (adding a bench, step 4) |
| Simulator profile assertions | Each network profile actually drops/reorders/duplicates |
| Fixture regeneration | Every generated golden is reproducible; recorded migration fixtures match their hashes |
| Traceability lint self-test | A fake requirement without a test is rejected by `check-trace` |
| Quarantine audit | Every quarantined test has an issue, an owner and a expiry |

These meta-tests are cheap and they keep the suite from decaying into an
expensive green light. When one of them fails, the problem is the test system,
which is exactly when it is most important to notice.

## 8. Open questions

1. **Register item needed: the per-PR gate-scene subset and lane packing** (MS-02).
   Chapter 25 §7 fixes which scenes gate a PR touching their crate; what remains
   open is how that subset, the canary and the microbenchmarks fit the 12-minute
   test tier and 8-minute bench lane inside the 25-minute pipeline. A decision is
   needed before the first bench gate is mandatory.
2. **Register item needed: canary cadence inside the bench lane** (MS-02). The
   canary is mandatory on every gate PR (25 REQ-PERF-015); it must stay inside the
   8-minute bench lane, and a lane that cannot absorb it is re-baselined rather
   than losing the control.
3. **Bench box ownership** (MS-02). A self-hosted machine needs a rota, spare
   parts and a calibration schedule; the alternative is noisy cloud runners.
4. **Divan vs criterion** (MS-02). Criterion is chosen for JSON change detection
   and statistics; divan's lower overhead may matter for sub-microsecond benches.
5. **Fixture hosting** (MS-13). Git LFS, release artifacts or regenerate-on-demand;
   the 300 MiB cap forces a choice before MS-13.
6. **Golden-image policy for shader packs** (MS-12). Do third-party packs get
   goldens, or only the sample pack shipped in-repo?
7. **Mutation-testing scope** (MS-10). Which modules beyond inventory, lighting,
   protocol and save justify the nightly minutes?
8. **Cross-platform aarch64 breadth** (MS-00). Linux aarch64 is planned; Windows
   on ARM and macOS Intel are release targets but slow CI runners.
9. **Public benchmark dashboard** (MS-16). Publishing per-commit numbers invites
   noise complaints; it also builds trust.
10. **Manual-checklist tooling** (MS-14). A Markdown file or a structured QA app
    with evidence attachments; the release gate needs the latter eventually.
