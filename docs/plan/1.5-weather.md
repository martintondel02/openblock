## 2. Weather state machine

| Phase | Duration (ticks) | Intensity target | Transition |
| --- | --- | --- | --- |
| `Clear` | 12,000–72,000 | 0 | always `Precipitating` |
| `Precipitating` | 3,000–12,000 | 0.65–1.0 | 15% `Thunder`, 85% `Clear` |
| `Thunder` | 3,600–12,000 | 0.85–1.0 | 30% `Precipitating`, 70% `Clear` |

- Bounds are inclusive. `epoch` starts at 0 and increments on every transition.
- Duration and transition roll come from `splitmix64(seed ^ WEATHER_STREAM ^ epoch)`,
  with `WEATHER_STREAM = 0x5745_4154_4845_5201`; the intensity target uses the
  same input with a second domain separator.
- Intensity is integer **permille** (`intensity_permille`, 0–1000), ramped by
  **5/tick** toward the phase target: at most **200 ticks** to any target. The
  fixed-point representation makes save/reload and `state_hash` exact.
- Weather light factor is fixed by phase: **1.0 clear / 0.8 rain / 0.6 thunder**.
  It is applied at query time only (`World::gameplay_light`), so stored light
  words, light hashes and remesh output are unaffected by a storm.
- `Host::set_weather_cycle(false)` is the `do_weather_cycle` gamerule equivalent
  (host config/setting, not a wire command). It freezes phase, remaining and
  intensity; lightning still rolls against the frozen thunder phase in tests.
  `Host::set_weather_state(phase, remaining, intensity_permille)` is the
  admin/test seam; normal clients cannot call it.

## 3. Persistence and migration

`level.txt` v1 is additive with a stable field order, one `key=value` per line:

```text
version=1
time=123456
weather_phase=precipitating
weather_remaining=5000
weather_intensity=777
weather_epoch=7
```

- A world from 1.4 or earlier has no `level.txt`: `player.txt` field 7 supplies
  `time`, and the weather machine starts deterministically in `Clear` from the
  world seed. The first save writes `level.txt`.
- Once present, `level.txt` is authoritative for world time; a differing
  `player.txt` clock is logged and ignored. A save/reload reproduces phase,
  remaining, intensity, epoch and the `state_hash` exactly.
- Unknown keys are ignored, an unsupported `version`, a missing/invalid `time`
  or a line without `=` rejects the file (warn + fall back to `player.txt`).
  With a valid phase but missing individual weather fields, the remaining
  duration defaults inside that phase's band and intensity starts at zero; a
  missing/invalid phase resets the weather block to the deterministic fresh
  clear state while keeping the clock.
- `world.obs` stays **v4** with only appended block ids; the registry
  fingerprint prefix acceptance is unchanged. `Host::state_hash` appends the
  weather tuple and every fire cell timer under new markers `0xF8`/`0xF9`.

`fire.txt` v1 is a header-free sidecar, one line per burning cell:

```text
x y z remaining_ticks
```

Rows are sorted by `(x,y,z)`, clamped to `1..=160`; a timer whose block is no
longer `openblock:fire` is dropped with a warning, and a missing file loads as
no fires. The fire **block id** still lives in `world.obs`; `fire.txt` only
carries the burn timers that the block palette cannot express.

## 4. Precipitation

`ob_worldgen` exposes pure helpers that never generate or load a chunk:

```rust
impl Generator {
    pub fn precipitation_at(&self, x: i32, z: i32) -> Precipitation;
    pub fn temperature_c_at(&self, x: i32, z: i32) -> f32;
}
impl Biome {
    pub const fn temperature_c(self, surface_y: i32) -> f32;
    pub const fn precipitation(self, surface_y: i32) -> Precipitation;
}
```

| Biome | Representative temperature | Precipitation |
| --- | --- | --- |
| Plains | +15 °C | rain |
| Forest | +13 °C | rain |
| Desert | +30 °C | **none** (dry) |
| Snowy taiga | −8 °C | snow |
| Mountains | +5 °C below the snow line, −3 °C at/above it | rain below, snow above |

The server maps these to `PrecipitationKind::{None,Rain,Snow}` and applies the
current phase (clear is always none). Rain hydrates a planted crop when the
crop column is rain and sky-exposed; the crop pass then swaps the farmland block
dry↔wet as before. Snow does not hydrate. Rain/snow on an exposed fire
extinguishes it; water in any of the six neighbours extinguishes it too.

## 5. Lightning

- Per tick during `Thunder`:
  `mix64(seed ^ WEATHER_STREAM ^ epoch ^ tick ^ LIGHTNING_ROLL_STREAM)` is
  reduced modulo `2,400,000`; a strike happens when the residual is below
  `intensity_permille`. This is exactly `intensity / 2,400` per tick (one strike
  per ~2,400 ticks at full intensity), with `LIGHTNING_ROLL_STREAM =
  0x9E37_79B9_7F4A_7C15`.
- Candidate columns are the sorted union of a 48-block radius around active
  players (network players in network mode; the internal player otherwise):
  resident chunk, precipitating column, solid non-fluid surface block, air
  above, and sky exposure from the heightmap plus a non-zero sky-light sample.
  No candidate means no strike.
- Target selection is a second deterministic hash
  `mix64(seed ^ WEATHER_STREAM ^ epoch ^ tick ^ LIGHTNING_TARGET_STREAM)`
  (`0xD1B5_4A32_D192_ED03`) modulo the candidate count. Candidate order is
  sorted `(x,z)`, so two hosts with the same seed, tick, player set and resident
  columns emit the identical event sequence.
- Effects in fixed order: player damage, mob damage, ignition, event:
  - players/mobs within 3 m take `10 HP × (1 − d/3)` through the normal armor
    path (`damage_with_outcome` / `damage_network_player`); mob deaths drop
    nothing and are replicated as despawns;
  - `ignite_fire(above)` places fire in the air above the struck block if the
    fire caps allow it (this is the normal block-edit/relight path);
  - one `LightningEvent { pos, block, ignited, flash }` is queued for the
    network layer.

## 6. Fire model and caps

- Block: `openblock:fire`, append-only **id 29**, texture layer **38** (`fire`),
  non-solid, non-opaque, `BlockShape::Cross`, emission `[15;3]`, attenuation
  `[0;3]`, hardness 0. Its block item appends after the frozen 1.2/1.3 item
  catalogue (creative item id **71**, so no existing item id moves); it has no
  natural drop.
- Timer: 160 ticks (8 s). The block emits light 15 through the normal
  `World::set_block` relight; ignition/removal queues a `BlockEdit`.
- Placement: normal survival and creative block placement detect the fire block
  and route through `Host::ignite_fire`, so a placed fire consumes one item in
  survival, gets a timer, and obeys both caps. It is not an inert map edit.
- Spread: every 40 ticks (four chances per cell) a **25%** deterministic roll
  (`seed ^ FIRE_SPREAD_STREAM ^ position ^ remaining`) converts one
  six-neighbour **flammable** block into fire. Spread consumes the block; the
  new cell gets a full 160-tick timer. Candidate order is sorted ascending
  `(x,y,z)`; the target index is a second hash.
- Flammable content: planks, log, leaves, crafting table, chest and both bed
  halves. `BlockType::flammable` is a pack field (default `false`); stone, dirt,
  water, torch and fire are not targets.
- Caps: **64** active fire cells world-wide, **8** per chunk. Ignition and spread
  fail at either cap, so a fire can never run away. Streaming an unloaded chunk
  removes its blocks (the existing streaming contract), so the fire pass drops
  an orphan timer rather than freezing it; there is nothing left to resume.
- Damage: players/mobs whose AABB overlaps a fire block take **1 HP/s**, applied
  once per 20 ticks (one armor durability event per second); mob deaths drop
  nothing.
- Extinguish: rain or snow on an open-sky fire (heightmap exposure) or water in
  the six-neighbourhood removes the block, timer and pending edit immediately.

## 7. Client / render / audio contract

### 7.1 Host API (server-side, for the integrated client and tests)

```rust
pub struct WeatherState { pub phase: WeatherPhase, pub remaining_ticks: u32,
                          pub intensity_permille: u16, pub epoch: u64 }
impl Host {
    pub fn weather(&self) -> &WeatherState;
    pub fn weather_phase(&self) -> WeatherPhase;
    pub fn weather_intensity(&self) -> f32;          // 0.0..=1.0
    pub fn weather_remaining_ticks(&self) -> u32;
    pub fn storm_epoch(&self) -> u64;
    pub fn is_thunder(&self) -> bool;
    pub fn is_precipitating(&self) -> bool;
    pub fn weather_factor(&self) -> f32;             // 1.0 / 0.8 / 0.6
    pub fn precipitation_at(&self, x: i32, z: i32) -> PrecipitationKind;
    pub fn precipitation_at_pos(&self, pos: BlockPos) -> PrecipitationKind;
    pub fn biome_name_at(&self, x: i32, z: i32) -> &'static str;
    pub fn rain_reaches(&self, pos: BlockPos) -> bool;
    pub fn sky_exposed(&self, pos: BlockPos) -> bool;
    pub fn tick_weather(&mut self);                  // Host::tick calls this
    pub fn weather_cycle_enabled(&self) -> bool;
    pub fn set_weather_cycle(&mut self, enabled: bool);
    pub fn set_weather_state(&mut self, phase, remaining, intensity_permille);
    pub fn take_lightning_events(&mut self) -> Vec<LightningEvent>;
    pub fn force_lightning_at(&mut self, top: BlockPos) -> Option<LightningEvent>;
    pub fn fires(&self) -> &BTreeMap<BlockPos, FireCell>;
    pub fn fire_count(&self) -> usize;
    pub fn fire_cell(&self, pos: BlockPos) -> Option<FireCell>;
    pub fn is_burning(&self, pos: BlockPos) -> bool;
    pub fn ignite_fire(&mut self, pos: BlockPos) -> bool;
    pub fn extinguish_fire(&mut self, pos: BlockPos) -> bool;
    pub fn force_spread_fire(&mut self, pos: BlockPos) -> bool; // admin/test
}
```

`Host::tick`/`Host::tick_network` order is deterministic:
`tick_count += 1 → weather phase/ramp and lightning scheduler/effects →
player/mobs/items → crops (weather-aware hydration) → fire
tick/extinguish/damage/spread`. A strike's new fire is therefore first processed
by the **same** tick's fire pass. That is intentional (the fire pass uses a
copied, sorted key list, so a newly ignited cell cannot change the current tick's
iteration order), but it does mean the ignition already has its 160-tick spread
chance on the strike tick.

### 7.2 Wire messages (protocol v5)

```jsonc
{ "type": "weather_sync",
  "phase": "clear" | "precipitating" | "thunder",
  "intensity": 0.0, "remaining_ticks": 30241, "epoch": 0,
  "precipitation": "none" | "rain" | "snow",
  "biome": "plains", "weather_factor": 1.0 }

{ "type": "lightning_strike",
  "pos": [0.5, 82.0, 0.5], "block": [0, 81, 0],
  "ignited": true, "flash": true }
```

`weather_sync` is sent on join and every 20 ticks (1 s) per player, because
`precipitation`/`biome` are resolved at that player's column. `lightning_strike`
is a one-shot; the accompanying fire placement arrives as an ordinary
`block_edit` with the session-local block id for `openblock:fire` (29 in the
base registry). Framing, the 2 MiB cap, chunk/light codecs and inventory
addressing are unchanged.

### 7.3 Render work (not in this slice)

- Environment: derive sky darkening/fog from `phase`, `intensity`,
  `weather_factor`; never advance the machine client-side.
- Particles: rain/snow within 16 m of the camera, cap 2,000, using
  `precipitation`/`biome`; splashes optional; particles must never enter the
  host hash.
- Lightning flash: one brightness pulse on `lightning_strike` where `flash`;
  do not infer a strike from block edits.
- Fire block: layer 38 (`fire`) as an animated cross cut-out, emission 15
  already reaches the mesher via light updates; billboard/sprite animation is a
  render concern.

### 7.4 Audio work (not in this slice)

- Rain loop / snow near-silence driven by `weather_sync` phase+intensity.
- One thunder one-shot per `lightning_strike`, delayed by `distance / 343 m·s⁻¹`
  from the listener; `pos` is the strike centre.
- Fire crackle/ambience is optional and must not affect simulation.

item placement and creative camera placement of fire through the timed

Loopback (`ob_server/tests/net_survival.rs`):
`protocol_v5_weather_sync_lightning_fire_and_reconnect_are_authoritative` covers
the initial `weather_sync`, forced thunder sync, forced strike + fire

## 9. Remaining work / risks

- **Render/client/audio** contracts above are not part of this server commit;
  another agent owns `crates/render`/`crates/client`. The procedural weather/fire
  audio is already committed separately (`358021d`), and the server slice never
  edits `crates/audio`.
- **Client display of v5**: a 1.4 client is rejected at the handshake; the v5
  client must ignore unknown future variants and reconcile `weather_sync` at 1 s
  cadence (interpolate intensity locally toward the target).
- **Release load tooling**: `scripts/load-gate.py` and `scripts/load-test.py`
  still hard-code protocol 4, so the unmodified quick gate fails the v5
  handshake. A local one-line `PROTOCOL_VERSION = 5` copy passes the quick gate
  (4/4 joins, 676 chunks, 19.99 TPS, p99 36.9 ms in this debug build, 0
  overruns). The release-tooling owner should bump both scripts; they are outside
  this commit's path set.
- **Per-dimension weather** remains the long-term spec (07 §3.13); this slice has
  one overworld machine because 1.5 has one dimension.
- **Fire sidecar reconciliation**: normal item/creative placement now goes
  through `ignite_fire`, but a block written by an external/admin tool or a
  pre-1.5 save can still hold `openblock:fire` without a `fire.txt` row. Such a
  cell is inert until extinguished or re-ignited; a load-time warning is not
  emitted because the scan is limited to saved rows.
- **Unloaded chunks**: streaming an unloaded chunk discards its blocks, so the
  fire pass drops the orphan timer rather than freezing it. Fire cannot survive
  leaving the resident set; this is consistent with all other block edits in
  unloaded chunks, not a fire-specific persistence guarantee.
- **No `do_fire_tick` gamerule yet**: fire always ticks. The host setting
  `set_weather_cycle` only freezes weather.
- **Sleep fast-forward**: `advance_single_sleep` jumps `tick_count` directly
  instead of running the weather/fire/crop passes for every skipped tick, so a
  storm and fire timers pause or advance only one tick per skip step during the
  sunrise fast-forward. This matches the pre-existing crop-skip behaviour and is
  left as a scheduling follow-up (`WeatherState::advance_by(ticks)`).
- **Lightning content tables** (transformations, rods/redstone) are 1.5+/1.6
  content work; this slice hard-codes damage/ignition as the interim model.
- **Performance**: candidate gathering is O(π·48²) only on a successful roll
  (~1/2,400 ticks); the fire pass is O(active cells) ≤ 64 with a per-tick copied
  key list. Measured cost is in §8.1 (weather machine 2.33 ns/tick, 64-cell fire
  pass 8.84–11.52 µs/tick, lightning 1.07 µs/tick over 24k ticks); a dedicated
  `cargo bench` harness is still not part of the gate.
