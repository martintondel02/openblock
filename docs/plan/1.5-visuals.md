## 2. Particle and renderer design

### 2.1 CPU model

`ob_render::particles` owns the public, deterministic simulation:

```rust
pub enum Precipitation { None, Rain, Snow }
pub enum ParticleKind { Rain, Snow, Smoke, Ember, Debris, Xp, Heart }

pub struct WeatherParticles {
    pub precipitation: Precipitation,
    pub intensity: f32,        // 0..=1
    pub wind: [f32; 2],        // m/s
    pub exposure: f32,         // 0 under a roof/underground, 1 open sky
    pub ground_y: f32,         // recycle weather drops at this height
}

pub struct ParticleSystem { /* splitmix64 rng + Vec<Particle> */ }
impl ParticleSystem {
    pub fn new(seed: u64) -> Self;
    pub fn update(&mut self, dt: f32, camera: [f32; 3], weather: WeatherParticles);
    pub fn prefill_weather(&mut self, camera: [f32; 3], weather: WeatherParticles);
    pub fn emit_fire(&mut self, positions: &[[f32; 3]], dt: f32, wind: [f32; 2]);
    pub fn spawn_explosion(&mut self, pos: [f32; 3], power: f32);
    pub fn spawn_lightning_strike(&mut self, pos: [f32; 3]);
    pub fn spawn_xp_pickup(&mut self, pos: [f32; 3], amount: u32);
    pub fn spawn_hearts(&mut self, pos: [f32; 3], count: usize);
    pub fn recenter_if_needed(&mut self, previous: [f32; 3], camera: [f32; 3]);
    pub fn instances(&mut self) -> &[ParticleInstance];
}

#[repr(C)] // 48 bytes, Pod
pub struct ParticleInstance {
    pub position: [f32; 3],
    pub size: [f32; 2],
    pub color: [f32; 4],
    pub rotation: f32,
    pub kind: u32,
    pub glow: f32,
}
```

Caps are hard: **4,096 live particles**, **2,048 precipitation**, **384 fire
effects**. Every burst checks the cap before pushing, so a hostile radius or a
pile of fires cannot grow the pool. Particle randomness is a seeded splitmix64
stream, making the same camera/weather/dt sequence byte-identical in tests and
screenshots; the client never feeds particle output back into simulation or the
host hash.

The simulation uses `f32`/plain arithmetic only, no allocation after capacity is
reserved, and `dt` is clamped to 0.1 s so a stalled frame cannot teleport
particles through geometry. Weather spawn is a uniform disc around the eye
(14 m) biased upward 3–11 m; drops are recycled horizontally beyond 26 m, below
`ground_y`, or when exposure drops to zero. Entering a roof clears existing
drops immediately; a partially exposed canopy fades them.

### 2.2 GPU pass

One pipeline and one vertex buffer; `draw(0..6, 0..count)` with
`step_mode = Instance`. The vertex stage expands a camera-facing quad from
`basis_right`/`basis_up` and the instance rotation; the fragment stage draws the
silhouette procedurally from `kind`:

| Kind | Shape |
| --- | --- |
| Rain | tapered vertical streak, camera-space (no texture) |
| Snow | soft six-point flake |
| Smoke | soft puff, grows with age |
| Ember | hot core + halo |
| Debris | rotating shard |
| XP | diamond spark |
| Heart | implicit heart curve |

Particles render after the opaque and water passes into the HDR target with
depth test `LessEqual`, depth writes **off**, and alpha blending. Fog fades alpha
to zero and a near fade keeps a drop from covering the eye. The pass reuses the
existing camera bind group (only binding 0); no extra uniform, texture, sampler
or bind group is created. `RenderStats::particle_instances` and
`particle_draw_calls` expose the counts; a frame with no particles records no
pass at all.

`SceneParams` gained two defaulted fields:

```rust
pub weather: WeatherVisual,                    // clear-weather default
pub particles: Option<&[ParticleInstance]>,     // None/empty = no pass
```

so every existing scene (menus, old screenshots, benchmarks) renders exactly
the v1.4 look unless weather is set.

### 2.3 Weather visuals

`EnvironmentVisual::with_weather` is a pure CPU function. It keeps the clear-sky
palette's luminance and then desaturates towards grey and darkens; this matters
because blending towards a fixed grey would make a midnight storm brighter than
a clear night. At full overcast the daylight factor is ~0.38, ambient ~0.54,
sun disc ~0.03, and stars/moon disappear. Snow adds a small cool horizon bounce.
`CameraUniform` carries one new `weather` row (intensity, storm, reserved,
reserved, offset 544; uniform now 560 bytes) used by the sky shader to lower the
cloud plane from 190 m to ~110 m at full storm, increase cloud coverage and
wind, darken cloud bodies and suppress the sun rim. Storm fog pulls the start and
end of `Camera::fog_range` inward (up to 45%/35%) with the same values on the
near and far paths, so the seam still matches.

Lightning is a **post-processing exposure lift**, not a scene light: the HDR
colour is multiplied by `1 + flash*3` before the ACES fit, so sky, terrain,
water and particles brighten together without washing the frame to flat grey.
The flash envelope decays at 6.5 s⁻¹ and the post pass has no extra texture or
pass. Explosions use the same mechanism with a much smaller amplitude.

## 3. Fire rendering

The content block (`openblock:fire`, layer 38, emission 15, cross) was already
authoritative; the previous renderer had two defects that made fire unreadable:

1. **Cross meshes were horizontal.** `mesh_cross` emitted the same horizontal
   square twice (both windings), so torches, wheat and fire were flat ground
   decals. It now emits two perpendicular **vertical** diagonal planes, each in
   both windings, with per-corner light/AO. This also fixes the 1.2 torch/farm
   presentation and is covered by the existing cross meshing tests.
2. **Fire had no procedural texture.** `texture_packs.rs` now generates a ragged
   teardrop flame cut-out (binary alpha, bright yellow core, orange/red rim,
   detached sparks) in all four styles, and `resource_pack` accepts
   `fire_0.png`/`fire_1.png`/`fire.png` from user packs.

The fragment shader recognises layer 38 and always samples mip 0 (alpha-cut-out
mips would average the thin flame away at distance), wobbles the UV with time
and world position, pulses the alpha threshold and writes a warm HDR colour
(most of the flame below the bloom threshold; only the core blooms). Fire
receives no scene light, so it reads the same in rain, darkness and overcast.
The block's emission 15 and the normal relight path provide the actual warm
block light; a large low-alpha ember billboard at each fire base adds a soft
warm halo, and `emit_fire` produces embers/smoke from nearby burning cells. In
rain the server extinguishes the block, and the client simply stops emitting.

`openblock:fire` maps to `ob_audio::Material::Fire`, so breaking/placing uses the
new dry-crackle variants, and the fire crackle loop is driven by the number of
burning blocks within 8 m (`fires / 4`, 0.8 ceiling).

## 4. Explosion, creeper and XP

- **Explosion.** A burst of smoke, debris, sparks and a short orange fireball
  (5–18 large emissive billboards), camera shake with squared distance falloff,
  a small exposure pulse, and `explosion_cue(distance)` with `world_pan`. The
  server owns block damage and fire; the client only presents the event.
- **Creeper.** Single-player reads the authoritative `Mob::fuse_timer` and
  computes a fuse progress: the avatar swells up to 1.3× and pulses white. The
  networked protocol has no fuse field, so multiplayer uses a proximity hiss
  warning (6 m, 6 s cooldown) and leaves the explosion cue authoritative; this is
  recorded as a limitation below.
- **XP/level.** `xpsync` pickups spawn green/yellow diamond sparks at the player
  and play `XpPickup`; a level increase plays `LevelUp`. Network `AttackResult`
  criticals play `CriticalHit`; nearby skeleton/spider mobs emit sparse rattle/
  chitter cues; arrow spawn/despawn events play `BowShoot`/`ArrowImpact`.
- **Hearts.** `spawn_hearts` is available for breeding feedback; the client only
  calls it from a cheap local hook when a breeding result is already on screen,
  so it is optional and never authoritative.

## 5. Protocol and client integration

The client consumes the concurrent protocol v5 messages without changing them:

```jsonc
{ "type": "weather_sync", "phase": "thunder", "intensity": 0.95,
  "remaining_ticks": 6300, "epoch": 9, "precipitation": "rain",
  "biome": "plains", "weather_factor": 0.6 }
{ "type": "lightning_strike", "pos": [x,y,z], "block": [x,y,z],
  "ignited": true, "flash": true }
```

`NetworkClient` keeps a sanitised `WeatherSnapshot` from the first/last sync and
emits `NetEvent::WeatherSynced` plus one `NetEvent::LightningStrike` per strike.
`WeatherPresentation` owns the local flash, shake, thunder queue, wind and HUD
state; it is reset on disconnect/reconnect. Single-player reads the same state
from the `Host` accessors (`weather_phase`, `weather_intensity`,
`precipitation_at_pos`, `biome_name_at`, `weather_factor`, `take_lightning_events`)
and drains `take_explosion_events`. No client path advances the weather machine,
ignites fire or predicts a strike.

Thunder is delayed by `distance / 343 m·s⁻¹` in a bounded 16-entry queue; the
first update after the delay plays `thunder_cue(distance)` with a yaw-relative
pan. Distant thunder (<96 m but outside the near clip) also gets an immediate
`LightningCrack`. Rain/snow/ambient loops are written every frame from the
authoritative phase (1.2 s mixer ramp), and all calls are no-ops when audio is
disabled or stubbed.

The compact HUD chip appears only when weather is active or flashing:
`Rain 80% 3:30 left factor 0.80 [sheltered] [FLASH]`. F3 adds three lines for
phase/tag/intensity/factor, precipitation/biome/remaining/epoch and lightning/
flash/thunder/shelter; the debug screenshot uses the same `DebugStats` fields.
The chip is pure presentation and takes no input.

## 6. Screenshots and capture modes

New run-only flags (all require `--screenshot PATH`, no window):

```text
--screenshot-weather=rain|thunder|snow
--screenshot-fire
--screenshot-explosion
```

Their scenes reuse the interactive particle/weather/audio mapping with synthetic
input: weather sets the host phase and pre-fills the local cloud; fire builds a
stone clearing with three burning log piles; explosion builds a rubble wall and
bursts at a fixed point. Captures are deterministic (fixed scene time, fixed
particle seed), 1280×720 RGBA PNG, and include the HUD.

## 7. Performance

Measured on the host (Ryzen 7 9800X3D, RADV RAPHAEL_MENDOCINO, integrated GPU),
release build, 1,920×1,080, High preset, native path, `render_distance_bench`
with the camera/time profile of the v1.4 report (`--view-distance 512 --radius
32 --eye-height 18 --pitch -0.25 --time 0.42 --scene-time 12`, offscreen readback
included):

| Run | p50 ms | p95 ms | Particle billboards | Draw cost |
| --- | ---: | ---: | ---: | --- |
| Clear baseline, trial 1 | 55.96 | 58.59 | 0 | no particle pass |
| Thunder, trial 1 | 55.00 | 58.77 | 1,700 | +1 draw, 560-byte uniform row |
| Clear baseline, trial 2 | 55.90 | 59.20 | 0 | no particle pass |
| Thunder, trial 2 | 56.02 | 59.85 | 1,700 | +1 draw |
| **Median p50 delta** | **−0.42** | +0.42 | | **≤ +1.0 ms target met** |

The storm run is not slower within noise: the closer fog wall removes more
fragments than the particle pass adds. The worst measured delta is **+0.12 ms**
p50. The absolute 55.9 ms baseline is **not** the 16.63 ms figure from the v1.3/
v1.4 reports on this host; repeated runs in this session reproduce ~55 ms even
with weather and particles off, so the same-session clear/storm pair is the
valid comparison. The 1.5 slice adds one 560-byte uniform row, one 192 KiB
instance buffer allocated once, and one draw call with no per-frame allocation
at steady state.

Particle CPU cost is bounded by the caps: 1,700 rain instances plus packing and
simulation stay well under 0.2 ms on this CPU; the GPU cost is one blended pass
over camera-local geometry. Fire/explosion bursts are capped at 384/4,096 and
allocate nothing after warm-up.

## 9. Limitations and remaining hooks

- **Absolute benchmark context.** The host reports ~55 ms p50 for the unchanged
  clear v1.4 scene at 1080p High, not the 16.6 ms in the earlier measurement note.
  The weather comparison is valid on this host; a clean bench box should re-run
  the absolute row before quoting a final number.
- **No point lights.** Fire/explosion light is baked emission plus a screen-space
  warm particle halo; there is no dynamic clustered point-light pass, so nearby
  terrain does not receive a time-varying orange pool.
- **Rain does not splash.** No splash rings/particle on ground impact yet.
- **Snow does not accumulate** and does not tint the ground; the server has no
  snow-layer block in 1.5.
- **Network creeper fuse.** Protocol v5 does not carry `fuse_timer`, so multiplayer
  uses a proximity hiss and no swell/flash; single-player uses the authoritative
  timer. A later protocol field can drive both from one visual.
- **Screen droplets/vignette.** The optional rain-on-screen droplets were not
  added; the storm look relies on particles, sky, fog and flash. A vignette is
  already part of the post grade.
- **Bow audio in single-player.** The single-player interactions have no ranged
  bow item in 1.5; arrow spawn/despawn cues cover the networked skeleton arrows.
  `BowShoot` is wired to projectile spawn events only.
- **Weather chip has no settings row.** It is automatic for active weather and
  can be hidden with the HUD toggle (F1); there is no separate "weather HUD"
  checkbox. F3 is the detailed debug toggle.
- **Particles are not shadow casters** and do not receive dynamic shadows; this
  is deliberate for cost and keeps the pass to one draw.
- **Flash is post-only.** It brightens the frame but does not cast a directional
  flash shadow or illuminate the world through a light; the ACES exposure lift is
  the budgeted approximation.
- **No protocol/server edits in this slice.** The client matches the in-progress
  v5 message names/fields as read from the tree; the renderer never depends on the
  protocol crate, and the server remains the only authority for weather, fire
  and lightning.

## Open questions

- Do we want dynamic point lights for fire/explosions, or are baked emission plus warm particle halos enough at 1.5 fidelity?
- Should precipitation use GPU-procedural particles with depth occlusion instead of the CPU sim when the particle budget grows (rain splashes/snow accumulation/screen droplets)?
- How should weather HUD/audio controls be exposed in Settings (separate weather/ambient rows vs current volume mapping)?
- Do we need screen-space rain droplets and wet-surface shading, and at which quality tier?
- Should the network creeper fuse timer be added to protocol v5 (for accurate swell/flash in multiplayer) now, or wait for a protocol bump with movement validation?
- Which far-terrain/weather interaction matters more: storm fog into the 8 km horizon or a visible rain curtain near the player?
