# 1.3 FSR 1.0 Integration: Upscaling, Settings and Measurement

> Status: implemented on `v1.3-dev` · Last updated: 2026-11-25
>
> This document records the FSR 1.0 integration, its measured cost on the
> reference-class integrated RADV machine, and the decision to keep it
> **off by default**. It complements [spec/04 §3.13.9](../spec/04-shaders-and-visuals.md#3139-fsr-10-integration-v13-optional),
> [spec/25](../spec/25-performance-budgets.md), [DEC-016](../decisions.md#dec-016--shading-pbr-lite-defaults-taa--render-scale-no-vendored-upscalers)
> and the far-terrain work in [1.3-far-terrain](1.3-far-terrain.md).

## 1. Goal

Let the player trade internal render resolution for frame time while keeping the
UI at native resolution, without changing the 8,192-block visual horizon or the
native rendering path. FSR 1.0 was chosen over FSR 2/3 and DLSS/XeSS because it is
MIT-licensed source code (not a binary SDK), needs no motion vectors or history,
and therefore does not add temporal ghosting or a per-frame history contract. It
is the one vendorable upscaler under DEC-016; TAA with render scale remains the
long-term default path.

The integration work was:

1. wire the self-contained module into the real `SceneRenderer`;
2. add the independent persisted quality row, live settings row, CLI override and
   F3/benchmark reporting;
3. measure it honestly at the 512-chunk visual distance.

## 2. Architecture

`crates/render/src/fsr.rs` (EASU + RCAS pipelines, sampler, uniforms and the
output-sized intermediate) and `crates/render/assets/fsr/` (WGSL ports and AMD's
MIT `LICENSE-FSR.txt`) are copied from the prototype unchanged in behaviour.
`crates/render/src/lib.rs` exports `pub mod fsr`. REUSE annotates the asset
directory as MIT with AMD's copyright; SPDX headers are in both WGSL files and
the module docs reproduce the full notice.

### 2.1 Render size versus display size

`frame::SceneRenderer` now keeps both sizes:

| Value | Used by |
| --- | --- |
| **display size** | window surface / offscreen colour texture, camera aspect, shadow-cascade fit, UI, readback, screenshot size, UI hit-testing |
| **render size** | HDR scene (`Rgba16Float`), depth, bloom mips, post uniform texel sizes, the internal LDR post image, EASU input |

`FsrQuality::render_size` (from the module) chooses an even, aspect-preserving
0.77/0.67/0.59/0.50 linear scale. The render size equals the display size when
FSR is off. The camera aspect stays the display aspect because FSR maps the full
render target to the full output; using the render aspect would stretch the image.

### 2.2 Frame order

Native path (unchanged, no FSR pass):

```
shadow cascades -> main -> sky -> water/outline -> bloom -> post -> UI
```

FSR path:

```
shadow cascades -> main -> sky -> water/outline -> bloom
  -> post (internal LDR at render size, display format)
  -> EASU (render -> output-resolution Rgba8Unorm intermediate)
  -> RCAS (intermediate -> display-sized sRGB output)
  -> UI at native resolution
```

The internal LDR target uses the display target's format so the two existing
post pipelines (`fs_post` / `fs_post_simple`) are reused unchanged. `PostUniform`
already receives the target size, so its `1/width`, `1/height` texel step is the
render size under FSR, which is what FXAA and bloom sampling need. UI is drawn
after the upscale and never passes through FSR. The native path takes exactly the
pre-v1.3 code path and never creates the upscaler; the only added work is an
`Option` check and a one-time output-size reconciliation at the top of `record`.

### 2.3 Resize, quality changes and fallback

- `Renderer::resize` and `OffscreenRenderer::resize` keep the surface/offscreen
  texture at display size and call `SceneRenderer::resize` with that display size.
  The scene targets and internal LDR target are reallocated at the new FSR render
  size; the upscaler itself is kept and its intermediate follows the output size.
- Changing the FSR row calls `set_graphics`, which reconfigures the FSR resources
  and reallocates the scene targets in one step (the shadow map is allocated once,
  not twice). The compiled FSR pipelines are reused across enabled presets; only
  the LDR target and the upscaler's intermediate change size. Switching Off drops
  the upscaler and restores native-size targets.
- `record` reconciles a display-size mismatch before sizing any pass, covering the
  first frame and odd capture sizes. A validation error scope stays clean across
  the FSR passes in the tests.
- FSR requires an sRGB 8-bit output (`Rgba8UnormSrgb` or `Bgra8UnormSrgb`) because
  the internal LDR target shares the display format and the post pipeline writes
  linear values; a non-sRGB or non-8-bit output logs once and renders natively
  instead of producing a gamma-broken image. Both shipped output formats are sRGB,
  so this is a guard, not a user-visible mode.
- Offscreen screenshots keep their display size: `--screenshot-size 960x540` still
  writes 960x540 RGBA, with the world rendered internally at the selected FSR
  scale and the UI at 960x540.

## 3. Settings, CLI and F3

`ob_core::config::Settings` gains `fsr_quality`:

| Value | Serde/CLI name | Linear scale |
| --- | --- | ---: |
| `Off` (default) | `off` | 1.00 |
| `UltraQuality` | `ultra_quality` | 0.77 |
| `Quality` | `quality` | 0.67 |
| `Balanced` | `balanced` | 0.59 |
| `Performance` | `performance` | 0.50 |

Unknown persisted names deserialize to `Off` without discarding the rest of the
settings document. FSR is an **independent row**: `apply_graphics_preset` never
changes it and changing it never marks the preset `Custom` (the design treats it
as a resolution/time trade-off, not a scene feature).

- **Settings UI (Graphics tab):** an `FSR` choice row cycles Off/Ultra
  Quality/Quality/Balanced/Performance. When active it shows the internal
  resolution from the live renderer, e.g. `Quality (858x482)`; a two-line footer
  hint explains the native UI and immediate application. The row applies live and
  persists immediately.
- **F3:** a dedicated right-column line,
  `FSR Quality 1286x724 -> 1920x1080 (0.67x)`, or `FSR native` when off. The
  existing full/compact layouts, column wrapping and GUI-scale tests stay green;
  the compact layout is unchanged because it deliberately keeps only identity,
  performance, position, vitals, world and target information.
- **CLI:** `openblock --fsr off|ultra_quality|quality|balanced|performance` is a
  run-only override, like `--view-distance`: it is applied to the in-memory
  settings for the windowed, offscreen screenshot and benchmark paths but is not
  written to `config.json`. Saving unrelated settings restores the persisted FSR
  row; editing the FSR row itself turns the value into a real preference.
  `--help`/`--version` document it.
- **Benchmark tool:** `render-distance-bench --fsr QUALITY`; the report prints the
  display size, internal size, FSR summary and FSR pass count.

## 4. Measurement method

Reference-class host used throughout: AMD Ryzen 7 9800X3D with integrated RADV
`RAPHAEL_MENDOCINO` (Vulkan), Fedora Linux 45, wgpu 30.0.2, seed 42, offscreen
`Rgba8UnormSrgb`, release build (thin LTO), `High` preset unless stated. Scene:
simulation radius 32 chunks (512 blocks) and view distance 512 chunks
(8,192 blocks), 4,225 columns, 2,620 near sections + 1,010 far batches, 47,950 far
quads; camera at spawn eye +18 m, pitch −0.25 rad, noon-ish environment. Harness:
`render-distance-bench --render-distance 32 --view-distance 512 --frames 240
--warmup 20 --graphics high --fsr QUALITY`; every measured frame includes the
blocking GPU→CPU readback, so absolute values are higher than a windowed
present-to-present frame. Percentiles are nearest-rank over 240 frames. The table
uses **paired runs from one session**; the native p50 is 5% above the recorded 720p
quiet-box baseline (11.19 ms) and 0.9% above the 1080p one (15.70 ms), so the useful
comparison is the delta within this table.

An isolated pass probe (50 back-to-back EASU+RCAS passes, one readback) measured
**3.5 ms/frame at 1280×720 output** and **7.8 ms/frame at 1920×1080** for an sRGB
input. The same pass on a non-sRGB (`Rgba8Unorm`) input measured 4.6 ms at 1080p,
so the sRGB gather/re-encode path is a large part of the cost on this GPU. The
record-side CPU cost is below 0.01 ms/frame.

## 5. Measurements

The final paired session used 240 measured frames after 20 warm-up frames. Native rows
are the control; every FSR row is the same scene, camera, preset and geometry, differing
only in the internal render size and the two FSR passes.

| Display | FSR row | Internal | p50 ms | p95 ms | p99 ms | p50 FPS | p95 FPS | Δ p50 vs native |
| --- | --- | --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 1280×720 | **Native (Off)** | 1280×720 | **11.79** | 13.11 | 13.38 | **83.3** | 76.3 | — |
| 1280×720 | Quality | 858×482 | 18.13 | 19.14 | 19.45 | 55.0 | 52.2 | **+6.34 ms (+53.8%)** |
| 1280×720 | Balanced | 756×426 | 18.46 | 19.74 | 20.26 | 54.0 | 50.7 | +6.67 ms (+56.6%) |
| 1280×720 | Performance | 640×360 | 17.35 | 18.88 | 19.92 | 56.9 | 52.9 | +5.56 ms (+47.2%) |
| 1920×1080 | **Native (Off)** | 1920×1080 | **15.84** | 16.53 | 16.91 | **62.6** | 60.5 | — |
| 1920×1080 | Quality | 1286×724 | 26.63 | 27.96 | 28.32 | 37.4 | 35.8 | **+10.79 ms (+68.1%)** |
| 1920×1080 | Balanced | 1134×638 | 24.00 | 25.95 | 26.67 | 41.3 | 38.5 | +8.16 ms (+51.5%) |
| 1920×1080 | Performance | 960×540 | 25.42 | 26.99 | 27.98 | 39.4 | 37.1 | +9.58 ms (+60.5%) |

Counters were identical across every row: 751 opaque draws (433 sections + 317 far batches
+ 1 far mesh), 7,649,574 submitted vertices, 19 water draws and 312 shadow draws. Native
recorded 9 passes (two shadow cascades, main, sky, water, three bloom, post); FSR recorded
11 (the same nine plus EASU and RCAS). RSS after build was 272–279 MiB and peak 277–282 MiB
across all rows — no measurable memory regression, because the smaller HDR/depth/bloom
targets offset the LDR target and the output-sized intermediate.

The native p50 is within 5% (720p) and 1% (1080p) of the previously recorded far-terrain
quiet-box baseline (11.19 / 15.70 ms), so the native path did not regress. But no FSR row
comes close to native: the best result is 17.35 ms at 720p and 24.00 ms at 1080p, i.e. 47–68%
**slower** than native. FSR does not pay for itself in this scene on this GPU.

### Why the expected gain did not appear

The isolated pass probe (§4) attributes 3.5 ms (720p output) and 7.8 ms (1080p output) to
EASU+RCAS alone. The render-size reduction saves much less than that:

- The scene is **not fill-rate bound** at this resolution on this GPU: shadows, geometry
  submission, vertex work and memory traffic dominate. Comparing Performance (0.50× area)
  with Quality (0.67×) changes p50 by only 0.8–1.2 ms, so the internal-resolution saving is
  small.
- The 12-gather EASU plus 3×3 RCAS is **bandwidth/ALU heavy**, and its 48-texel footprint
  competes with the 32 MB shadow map. With shadows disabled the FSR delta at 720p fell from
  roughly +7.3 ms to +2.0–2.6 ms; with Low (1024²) shadows it was +3.2 ms, and with Ultra
  (2048², 5×5 PCF) +6.4 ms. The larger the shadow working set, the worse FSR performs.
- The sRGB input path is a measurable part of the pass: the same probe with a non-sRGB
  `Rgba8Unorm` input measured 4.6 ms at 1080p instead of 7.8 ms. Even that saving would not
  make FSR faster than native here.
- FSR only roughly broke even in a small 640×360 window (4.45 ms vs 4.61 ms native in a
  short High-preset probe), where the output-sized intermediate stays cache-resident.

Visual inspection: Quality and Performance are visibly softer than native on foliage,
block edges and distant trees, as expected from a 0.67×/0.50× internal image; RCAS keeps
edges from turning mushy and the clamped kernel suppresses obvious ringing. The far horizon
and clouds upscale smoothly. The settings panel and F3 text are unfiltered and pixel-crisp
in every capture, confirming that UI bypasses FSR. Sharpness itself is acceptable for an
optional mode; the problem is that it costs frame time rather than saving it.


## 7. Limitations

- **Spatial only.** FSR 1.0 has no motion vectors, jitter or history. It cannot
  recover sub-pixel detail (unlike FSR 2/3 or TAA), and it can shimmer on thin
  geometry when the camera moves. FXAA-lite can remain enabled at render size;
  the two are independent.
- **Gamma/perceptual contract.** EASU expects perceptual input. The integration
  uses an sRGB internal LDR target and re-encodes gathered values in EASU and
  decodes in RCAS. A non-sRGB output would receive perceptual values; no such
  output is shipped today.
- **Intermediate memory.** The upscaler owns one output-sized `Rgba8Unorm`
  intermediate (8.3 MB at 1080p, 3.7 MB at 720p) plus the internal LDR post target
  (3.7 MB at 1080p Quality, 1.7 MB at 720p Quality). Scene HDR/depth/bloom targets
  shrink with the render size, so peak RSS stayed within run-to-run noise
  (277–282 MiB FSR vs 278–282 MiB native in the paired session).
- **Unsupported formats.** The integration requires an sRGB 8-bit output
  (`Rgba8UnormSrgb`/`Bgra8UnormSrgb`) because its internal LDR target shares the
  display format and the post shader writes linear values. A non-sRGB surface or
  a 16-bit/HDR output falls back to native with a single log line; no shipped path
  uses one.
- **RCAS sharpness is fixed** at the reference 0.20 stops; there is no separate
  sharpness row.
- **Cost on this GPU.** The 12-gather EASU plus 3×3 RCAS is bandwidth/ALU heavy on
  an integrated GPU, especially after the 32 MB shadow-map traffic; see §5. FSR is
  therefore off by default and is not a recommended way to reach 60 FPS at
  1080p/512 chunks on the reference-class integrated RADV machine.
- **No dynamic resolution.** Presets are discrete; there is no automatic scale
  adaptation or frame-rate target.
- **DEC-016 note.** DEC-016 says no upscaler is vendored. FSR 1.0 is source under
  MIT and not a binary SDK, which the integration treats as the intended exception;
  a formal decision amendment should record that reading.

## 8. Tests

- `ob_core`: default `Off`, serde round-trip for all five names, unknown persisted
  value → `Off` while the rest of the document loads, missing field → `Off`,
  clamp/independence from presets.
- `ob_render`: FSR module unit tests and GPU tests (shader validation, EASU/RCAS
  sharpness vs bilinear, resize, formats, error paths); integration tests for
  1080p/720p/odd-size output, display-size readback, internal-size reallocation on
  resize and quality change, native UI pixels after the upscale, and unsupported
  format fallback.
- `ob_client`: Settings row label/value/cycling and the no-Custom rule, CLI parsing
  and run-only behaviour, mapping to the renderer enum, F3 line and layout tests.
- `ob_tools`: `--fsr` parsing/order independence, no-Custom rule, report fields
  (`targets … internal`, `fsr:`, FSR pass count).

## 9. Recommendation

Keep **`Off` as the default** and keep the feature opt-in. On the measured
reference-class integrated GPU it is a clear loss at 720p and 1080p with High
shadows, and roughly break-even only at small windows (640×360). The scene is not
fill-rate bound enough for a 0.67× scale to pay for FSR1's gather bandwidth, and
the 48-texel EASU footprint competes with the 32 MB shadow map for memory
bandwidth. A discrete GPU with more bandwidth may see a gain, and the settings row
makes that testable, but no such measurement exists in this repository.

If FSR is to be made competitive on integrated hardware, the next steps are:
use a non-sRGB internal LDR target with an explicit post sRGB encode (the pass
probe suggests ~40% of the FSR cost), investigate a compute-shader EASU with
fewer texture fetches, and compare against the existing FXAA+0.85 render-scale
path once TAA lands.
