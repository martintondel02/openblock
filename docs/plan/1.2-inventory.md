# 1.2 "Light & Home" — 36-slot inventory and protocol v3

> Status: implementation note for the 1.2 inventory slice
> Scope owner: inventory/protocol/client/server network paths
> Related: [`1.1-1.4-feature-waves.md`](1.1-1.4-feature-waves.md) §3,
> [`../spec/11-inventory-crafting-items.md`](../spec/11-inventory-crafting-items.md),
> [`../spec/18-networking-multiplayer.md`](../spec/18-networking-multiplayer.md)

## 1. Why

1.1 shipped a nine-slot hotbar and four armor slots. Chests were the only
storage, so a player who mined more than nine stacks had to shuttle through a
chest. 1.2 adds the standard 9 hotbar + 27 main + 4 equipment layout and raises
the interim wire protocol to v3 so a 1.1 peer cannot silently read main stacks
as armor.

The slice deliberately keeps the **17-action binding table unchanged**. All
inventory interaction uses the existing Inventory (`E`) binding plus mouse
clicks in the inventory screen; no new default keybind or action exists.

## 2. Slot scheme (protocol v3)

| Address | Meaning |
| --- | --- |
| `0..9` | hotbar, in slot order (unchanged from 1.1) |
| `9..36` | main inventory, 27 slots in row-major order |
| `36..40` | equipment: helmet, chestplate, leggings, boots |
| `100..` | open furnace (3) or chest (27) window slots, unchanged |

`ob_protocol` exports `HOTBAR_SLOTS = 9`, `MAIN_SLOTS = 27`,
`INVENTORY_SLOTS = 36`, `MAIN_SLOT_START = 9`,
`EQUIPMENT_SLOT_START = 36` and `SLOT_WINDOW_START = 100`.
`ServerMessage::InventorySync` now carries both `hotbar: [Option<ItemStackDto>; 9]`
and `main: [Option<ItemStackDto>; 27]` plus the unchanged `selected` and
`equipment: [Option<ItemStackDto>; 4]`. The JSON framing, the 2 MiB frame cap
and the chunk codec are unchanged.

`PROTOCOL_VERSION` is **3** in both `ob_protocol` and the duplicated
`ob_core::config` mirror. Every pinned test was updated. The server rejects a
v1/v2 `hello` with
`protocol_mismatch: server protocol 3, client sent N; 1.1 and older clients must
upgrade to a 1.2+ build`; the client reports the same mismatch before any state
is exchanged. This is the safety property: old clients fail before
`inventory_sync` can be misinterpreted.

## 3. Server changes

### 3.1 Single-player `Host`

`Host::inventory` grew from `[Option<ItemStack>; 9]` to
`[Option<ItemStack>; 36]`; `HOTBAR_SLOTS` remains 9 and new `MAIN_SLOTS = 27`,
`INVENTORY_SLOTS = 36` constants document the split. Because the array order is
wire-slot order, all existing slot-index code (selected slot, tool wear,
`consume_selected`, crafting ingredient scans) keeps working for the hotbar;
main slots simply participate in the same scans.

New APIs:

* `Host::move_inventory_items(from, to, count) -> Result<bool, &'static str>`
  merges a compatible stack up to the content `max_stack`, fills an empty
  slot, and only swaps incompatible stacks when the whole source stack moves.
  It returns `invalid_slot`, `same_slot`, `empty_source`, `invalid_count`,
  `destination_full` or `destination_occupied` without creating or destroying
  items.
* `Host::quick_transfer_inventory_slot(slot)` implements the shift-click rule:
  hotbar `0..9` -> first compatible/empty main slot, or main `9..36` -> first
  compatible/empty hotbar slot; `Err("no_room")` leaves the stack untouched.

`Host::give_item`/`give_stack`/`insert_inventory_stack` now fill in slot order:
compatible stacks are topped up first (hotbar before main because those are
lower indices), then empty slots from hotbar 0 to main 35. A full inventory
returns the whole remainder, which the caller leaves as an item entity.
`equip_armor` accepts any player inventory slot (hotbar or main) and still
swaps the displaced piece into the freed source slot; `unequip_armor` searches
all 36 slots for a free one. Death/respawn keeps inventory and equipment
exactly as in 1.1.

### 3.2 Network players

`ServerPlayer.inventory` is 36 slots. The `with_network_player_action` bridge
copies the larger array in and out unchanged, so block actions, eating, tool
wear and loot drops reuse the single-player rules. `InventorySync` is built
from `player.inventory[0..9]` and `[9..36]` plus the four equipment slots.

`network_inventory_move`/`network_inventory_move_checked` parse v3 addresses:
`0..36` player, `36..40` equipment, `100..` window. Window destinations in
`9..36` are valid, so furnace output may be taken into the main inventory (the
output slot remains take-only and never accepts a swap). Equipment moves keep
their 1.1 rules: one armor piece, the right armor slot, no equipment/window
direct moves. Anti-dupe validation is unchanged: counts must be positive and
not exceed the source, incompatible partial moves are rejected, and window
moves revalidate ownership, block identity, block-entity existence and the 6 m
distance before writing either slot.

Pickup calls `give_network_stack`, which uses the same 36-slot insertion order;
`network_players.txt` writes `i<slot>` for every non-empty player slot
(including main) and keeps `e<slot>` for the four equipment indices.

### 3.3 Save migration

`inventory.txt` keeps its header-free `slot item count [durability]` format:

* old 1.1 rows `0..8` load into the hotbar and leave all 27 main slots empty;
* new rows `9..35` load into main slots;
* rows `36+`, unknown items, bad counts and malformed lines are dropped with a
  warning (never clamped onto a valid slot);
* saves write only non-empty slots, so a 1.1 file reopened and saved gains main
  rows only when main items exist.

`network_players.txt` keeps the same token grammar. A 1.1 record with
`i0..i8` and `e0..e3` restores unchanged; new records may add `i9..i35`.
Equipment addresses in the sidecar remain equipment-array indices `e0..e3`;
the wire `36..40` remap is protocol-only.

The smoke hash for seed 42 is **unchanged** at
`eba0c42219691190` (old and new) with an empty inventory: the state hash still writes each
non-empty slot's index as a `u8` (now up to 35), so a save with main-inventory
items changes the hash as intended while 1.1-compatible states do not.

## 4. Client changes

### 4.1 Network state and protocol client

`SurvivalState.inventory` is now `[Option<ItemStack>; 36]`.
`apply_inventory` consumes both the hotbar and main arrays; unknown item names
still become empty rather than poisoning the slot. `equipment_address` returns
the v3 addresses `36..40` (a unit test pins this), while container cursor
addresses and `SlotId::Hotbar` remain hotbar-only. `NetworkClient::inventory`
returns the full 36 slots and the container snapshot still takes the first nine
for the unchanged hotbar strip in chest/furnace screens.

Two new network intents make the inventory screen usable without adding a
protocol transaction for the cursor:

* `NetworkClient::quick_transfer_inventory(slot)` computes the destination with
  the same shared helper as single-player and sends one `inventory_move`.
* `NetworkClient::equip_inventory_slot(slot)` uses the existing `equip` intent
  for a hotbar piece and `inventory_move(slot, 36+armor_index, 1)` for a main
  piece.

### 4.2 Inventory screen

Both single-player `App` and `NetApp` use the same `inventory` module and the
same UI state. The survival panel is now four nine-slot rows (three main rows
above the hotbar row) plus the armor row. Section labels are **Armor**,
**Main** and **Hotbar**; the title remains "Inventory" in the existing bitmap
heading style, body text remains Monocraft, and no unrelated styling changed.

Layout rules:

* regular 1280x720: 48 px slots, eight section labels, 124 px footer;
* compact (height < 560 logical px, including 960x540 at 125% = 768x432):
  smaller armor slots, tighter rows, 96 px footer and scaled footer controls;
* the layout also clamps to the logical 640x360 target from the GUI-scale
  matrix without clipping slots, armor or controls.

The footer still shows the hovered item name, tool/armor durability, food,
fuel, block hardness and crafting hints. Control hints document the new
interactions without adding keys:

```
Click pick/place  Shift quick-move  Armor equip
Arrows/Wheel  Enter use  C craft  E/Esc close
```

Interaction (both paths use `inventory::click_cursor_slot`):

* click a main stack: it becomes a pointer preview (highlighted source);
* click a hotbar/main slot: one authoritative move from preview source to the
  target (clicking the source again cancels);
* Shift+click: whole-stack quick transfer between hotbar and main; armor is
  equipped instead;
* click armor: equip the held matching piece, or unequip an occupied armor slot;
* click a hotbar slot with no preview: select that hotbar slot and close, the
  pre-1.2 behaviour; Enter on a main slot starts/cancels/completes the same
  preview so keyboard-only play works.
* single-player applies the move directly through `Host::move_inventory_items`;
  network play sends one `inventory_move` and waits for the authoritative
  `inventory_sync` (no local inventory mutation, no double-click duplication).

The hotbar HUD, creative palette, crafting screen and chest/furnace screens
keep their 1.1 layout. Container slot ranges are unchanged (furnace `100..103`,
chest `100..127`); the only range change is that a furnace output can now be
taken into any player slot, not only the hotbar.

## 6. Follow-ups and remaining risks

* **Container main rows.** Chest/furnace screens still show only the hotbar
  strip, matching 1.1; moving items to/from the 27 main slots happens in the
  inventory screen. Adding the main rows to container windows is a natural
  1.3 task (spec §3.3 expects container + main + hotbar).
* **Network crafting.** The dedicated server still has no crafting intent, so
  the NetApp inventory keeps the "Crafting is not available in multiplayer yet"
  hint. The single-player crafting screen scans all 36 slots.
* **Drag/double-click.** Click-to-pick/place and shift-click are implemented and
  tested; a true drag gesture with cursor prediction, gather/double-click and
  right-click half-stack in the inventory are not. They reuse the existing
  `inventory_move` intent when added.
* **Offhand slot 40** from the normative 41-slot design is reserved but not
  implemented; equipment addresses already match `36..40`, so adding offhand
  later does not renumber armor again.
* **Old sidecar rows outside 0..36** are dropped by design; a hand-edited file
  used to be clamped to slot 8, which could hide corruption. Players upgrading
  from 1.1 only have rows 0..8 and are unaffected.
* **Render integration.** The screenshots and visual check must be repeated on
  the final render build. The inventory code itself has no renderer dependency
  beyond `UiFrame`.
