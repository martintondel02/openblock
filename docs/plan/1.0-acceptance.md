# OpenBlock 1.0 acceptance sweep

> Status: complete · Last updated: 2026-11-25
> Scope: strict end-to-end gameplay-loop acceptance and bug bash for
> **1.0.0**, exercised through the `ob_server`, `ob_sim`, `ob_content` and
> `ob_worldgen` public APIs. Client UI is audited separately by the client/UI
> agent; this report does not grade rendering, menus or accessibility.
>
> Depends on: [1.0 scope](1.0-scope.md), [survival rules](../spec/08-gameplay-survival.md),
> [entities and AI](../spec/09-entities-ai.md), [inventory and crafting](../spec/11-inventory-crafting-items.md),
> [worldgen](../spec/06-worldgen.md).

## Result summary

The 1.0 survival loop is **playable end to end** with the deterministic seed
`42`. The automated acceptance suite starts from a fresh world, verifies spawn
safety and starter resources within 32 m, and then performs the full wood ->
stone -> coal -> iron -> food -> chest -> save/reload loop. A second scenario
runs the same loop's multiplayer-critical path against a real loopback
`DedicatedServer` using raw protocol v2 frames.

Two real bugs were found and fixed:

1. A **dead survival player could still break and place blocks** through the
   shared host action path. The network intent path already rejected dead
   players, but single-player host authority did not. Fixed in `ob_server`.
2. The **world spawn could move across save/reload** for far spawn candidates,
   and one seed started inside a tree. The fallback surface height was used when
   the candidate column was not streamed yet; after a reload the loaded tree
   canopy won. Spawn is now resolved against a generated safe column (solid dry
   surface, no feature above, two clear cells) and persisted in `spawn.txt`.

No balance tuning changes were made: the measured food, zombie, ore, tool,
fuel and armour numbers form a coherent loop. Three items are flagged for a
later human playtest rather than mechanically changed here (see
[playability audit](#playability-and-balance-audit)).

## Commands and environment

All commands run without a window or GPU, in `/tmp/ob-play`:

```sh
# Primary acceptance file (single-player, spawn regression, edge/fuzz, multiplayer)
CARGO_TARGET_DIR=/home/martintondel/Projects/openblock/target-1.0-accept \
  ./dev-cargo test -p ob_server --test acceptance

# Package suite required by the release gate
CARGO_TARGET_DIR=/home/martintondel/Projects/openblock/target-1.0-accept \
  ./dev-cargo test -p ob_server -p ob_sim -p ob_content -p ob_worldgen

# Quality gates
CARGO_TARGET_DIR=/home/martintondel/Projects/openblock/target-1.0-accept \
  ./dev-cargo clippy --workspace --all-targets -- -D warnings
CARGO_TARGET_DIR=/home/martintondel/Projects/openblock/target-1.0-accept \
  ./dev-cargo fmt --all -- --check
RUSTDOCFLAGS="-D warnings" CARGO_TARGET_DIR=/home/martintondel/Projects/openblock/target-1.0-accept \
  ./dev-cargo doc --workspace --no-deps
python3 .github/scripts/check-docs.py
```

The acceptance tests use `std::env::temp_dir()` for worlds, bind only
`127.0.0.1:0`, and never open a window. The single-player scenarios use no
wall-clock sleeps; the multiplayer scenario waits on protocol frames and the
server's real 20 Hz tick, as a real client does.

### Single-player scenario detail (seed 42)

1. Fresh world: spawn is at `(0.5, 81.0, 0.5)` on grass. The feet/head cells are
   air, the surface is solid, eight blocks of spawn crust are solid, and the
   player remains stationary and undamaged for 40 ticks.
2. Starter scan within 32 blocks of spawn: 293 logs, 2,743 leaves, 2,772 coal
   ore and 1,440 iron ore blocks (plus 285,655 stone in the y=0..160 slice)
   are present across the streamed chunks. The nearest tree is 5 m away (4 blocks Chebyshev) and is a
   real trunk with canopy; nearest coal is inside its documented `y=5..96` band
   and nearest iron
   inside `y=5..64`. A five-seed probe found the nearest tree at 3.6-60 m
   (desert seeds 1/1234 at 46-60 m, still inside the default render distance);
   seed 42 is the acceptance baseline and has the 5 m starter tree.
3. A small flat 9x9 test yard is built around spawn (test scaffolding only for
   deterministic placement and combat) and a crafting table, chest and furnace
   are placed through the real survival placement action.
4. Eight natural logs are mined by an empty hand and picked up. Eight planks
   recipes, three stick recipes and the table recipe run through
   `Host::craft`; table-gated recipes report `0` before placement and become
   available after.
5. Wooden pickaxe and axe are crafted. Eleven natural stone blocks are mined
   with the wooden pickaxe (1 block = 1 cobblestone) and a stone pickaxe is
   crafted. Three coal and eleven iron ore blocks are then mined with the stone
   pickaxe; tier gates and drops are asserted.
6. Eight cobblestone become a furnace. Ten raw iron plus two coal smelt in
   2,200 ticks (14 smelts would also fit the 3,200-tick fuel budget). Ten iron
   ingots become an iron pickaxe, iron sword and iron helmet; item totals are
   exact.
7. A four-block fall is taken with the iron helmet equipped; health drops but
   the player survives. Four cows are spawned through the public mob API and
   killed with the iron sword; four leather and four raw beef are picked up.
   The beef is cooked in 900 ticks. Hunger is staged to 10, cooked beef restores
   it to 18, and the stack shrinks by one. Four leather become leather boots,
   which are equipped with the helmet (armour defence 3).
8. A zombie is spawned through the public API and killed with the iron sword.
   A chest deposit/withdraw is performed. The chest and furnace retain contents
   and a mid-smelt state (one raw iron input plus one coal) is left for the save.
9. Lethal damage sets `dead`, respawn restores health/hunger to 20 at the world
   spawn, and the inventory and equipped armour are kept.
10. `Host::save` is followed by a full reopen and streaming convergence. The
    state hash (including the persisted spawn point), tick count, position,
    inventory, equipment, furnaces and chests are all identical.

### Multiplayer scenario detail

The loopback test starts a survival `DedicatedServer` with the same deterministic
seed and world shape. A raw TCP client speaks the public `ob_protocol` v2
messages (not host-only helpers):

- handshake and initial inventory/vitals/entity snapshot;
- break a surface block by hand and observe the authoritative dirt pickup via
  `InventorySync`, then place it back and observe consumption;
- place a furnace, `UseBlock`, move raw iron and coal into slots 100/101, wait
  for the real 200-tick smelt to produce an ingot, move slot 102 to the hotbar,
  and close the window;
- spawn and kill a cow with a wooden sword, waiting for the replicated item
  spawn and picked-up despawn;
- lethal admin damage -> `Death`, `Respawn` at the server spawn with inventory
  retained;
- stage vitals (16 health / 12 hunger), move 2 m, disconnect by name, reconnect,
  and verify vitals, inventory and position restore;
- stop the server, reopen the world, and verify the saved network player and
  furnace block entity.

Runtime: the whole multiplayer scenario is dominated by the 200-tick furnace
smelt. The final `cargo test --test acceptance` run reports **7 passed, 0
failed in 12.48 s** (14.3 s wall including the incremental build); the
single-player scenario is about **0.3 s**, the spawn regression about **0.1 s**
and the edge/fuzz tests together about **0.3 s**. The whole file is comfortably
below the 60 s budget and is deterministic (fixed seed, fixed tick counts, no
wall-clock decisions in the single-player paths).

## Playability and balance audit

Numbers are the current `openblock:base` implementation, not the fuller 08
balance profile described in the spec. The audit asks whether the loop is
playable or trivial, not whether every parity number is present.

| Area | Measured implementation | Verdict |
| --- | --- | --- |
| Hunger | Idle 0.005 pt/s; walking ≈0.048 pt/s (4.317 m/s); jump 0.03. 20 hunger ≈ 7 min of walking, ≈ 66 min idle. Regen at hunger ≥18 heals 1 HP / 4 s; starvation 1 HP / 4 s. | Soft timer, not a starvation treadmill. Fine for 1.0. |
| Food supply | Apple 6, raw beef 3, cooked beef 8, cooked porkchop 8; one cooked beef ≈ 2.8 min walking. Cows drop beef + leather, passive cap 10, natural spawns every 20 ticks. | Plentiful; hunger is rarely lethal. Accepted simplification. |
| Ore density and gates | Coal 9‰ of stone, `y=5..96`, tier 1; iron 5‰, `y=5..64`, tier 2; copper 4‰, `y=24..96`, tier 2. The 32 m seed-42 scan finds thousands of coal/iron blocks; a five-seed probe found stone/coal/iron under or within 5 m horizontally of spawn (at depth). | Progression is reachable quickly; no density change needed. |
| Starter wood | Seed 42 tree at 5 m. Treeless-within-32 desert seeds 1/1234 have their nearest tree at 46-60 m (default render distance is 96 m). | Playable but slower on desert spawns; accepted biome variety, no spawn override added. |
| Tool durability | Wood 59, stone 131, iron 251; one point per block/hit. Acceptance's full tool chain used 23 mining actions and did not threaten the stone pick. | Generous, not trivial (tier and slot costs remain). |
| Furnace fuel | Coal/charcoal 1,600 ticks = exactly 8 smelts; planks/log 300 = 1.5; stick 100 = 0.5. Ten iron + four beef used two coal with burn to spare. | Coherent; no change. |
| Armour | Leather 7 defense total, iron 15, cap 20, 4% per point (28%/60%/80%). Acceptance's mixed set gives 3 points (12%). Wears one point per damaging hit. | Coherent for 1.0; iron does not reach the cap, leaving post-1.0 room. |
| Zombies | 20 HP, 3 damage per 1 s attack, 2.2 m/s; wooden sword 4 damage (5 hits), iron sword 6 (4 hits). Unarmoured time-to-death ≈ 6.7 s, full iron ≈ 1.2 damage/s. | Challenging but escapable; night is the intended risk. |
| Spawn safety | 5x5 protected chunk square, 8-block crust; new safe-column resolver also rejects trees/features and cave entrances at the candidate column. | Safe at creation; spawn is now stable and persisted. |
| Inventory | Nine hotbar slots only. The full loop had to deposit planks/wood axe in the chest before animal drops. | Tight but workable; the chest is part of the loop, not an optional extra. |

No tuning change was clearly required by the automated evidence. Three
observations are recorded for human playtest instead:

- the first night can spawn up to eight zombies; no bed/torch exists in 1.0, so
  a new player's first night is the hardest gate;
- leather armour costs 24 leather (24 cows) for 7 defense while iron costs 24
  ingots for 15 defense, so leather is a vanity/stopgap tier;
- full leather/iron sets do not fit together with tools, food and blocks in the
  nine-slot hotbar; chest shuttling is necessary.

## Bugs found and fixed

### 1. Dead players could edit the world

- **File:** `crates/server/src/lib.rs`
- **Symptom:** `Host::apply_action_with_outcome` performed survival break/place
  while `player.dead` was true. The network handler rejects dead intents, but
  the shared single-player path did not, so a client-side death-screen bug (or a
  direct host caller) could mine and build while dead.
- **Fix:** return an unchanged `ActionOutcome` immediately when the player is
  dead, before either mode branch. The network path keeps its earlier rejection.
- **Regression:** `dead_survival_player_cannot_break_or_place` in
  `crates/server/tests/acceptance.rs`.

### 2. World spawn moved across reload and could start inside a tree

- **File:** `crates/server/src/lib.rs`
- **Symptom:** for far spawn candidates (e.g. seed 29 at `(56, 0)`), the fresh
  host used the generator fallback height because the candidate column was not
  streamed yet, placing feet at `y=67` inside a tree trunk. After reload the
  loaded canopy raised the surface and the spawn moved to `y=72`. Respawn points
  therefore disagreed between sessions.
- **Fix:** a new `Host::resolve_spawn` generates each candidate column before
  reading it, accepts only a solid dry surface with no feature above and two
  clear feet/head cells, and the chosen point is written to the additive
  `spawn.txt` sidecar in `Host::save` and preferred on open. Older worlds without
  the sidecar resolve once and persist on their next save.
- **Regression:** `spawn_is_safe_and_stable_across_reopen_for_far_candidates`
  covers seeds 42, 3, 29 and 94 (seed 29 is the previously failing case).

## Known accepted limitations (1.0)

- **Nine-slot hotbar only.** There is no 27-slot main inventory, offhand or
  cursor stack; containers are the storage extension. This is the shipped 1.0
  UI/data model (README documents the nine-slot hotbar).
- **Death keeps inventory and equipment.** No death drops, XP or keep-inventory
  rule exists in this slice. Network and single-player both retain the
  inventory on respawn, as documented on `Host::respawn`.
- **No torches, block light, farming, breeding, beds or weather.** The scope
  defers these; caves and night use the simplified time/depth model.
- **Single-player container/craft/equip APIs trust the local UI while dead.**
  Network intents are rejected; the host slot APIs intentionally do not validate
  liveness or reach (documented in `block_entities`). Only world edits were
  hardened by this sweep.
- **Spawn is safe at creation, not continuously revalidated.** If the player
  mines the spawn column or a tree grows into it (no growth in 1.0), respawn may
  need a better safe-spawn search; the current 1.0 contract stores one point.
- **Client-side movement in multiplayer**, as documented in the 1.0 scope.
- **New additive sidecar:** `spawn.txt`. It does not change save format v4 and
  is copied by the existing world-directory backup workflow; old worlds compute
  a spawn once and persist it on the next save.
- **No natural first-night balancing data from a human session.** The numbers
  are internally coherent, but the three observations above need a playtest.

## Open questions

- Should leather armour recipes be cheaper (or leather armour removed) given
  iron is easier per defense point?
- Is the first night's zombie pressure acceptable without torches/beds, or
  should natural hostile caps/damage be reduced for 1.0.1?
- Should respawn revalidate the stored spawn column (safe-spawn search) instead
  of trusting the point stored at world creation?
- Should the remaining single-player slot/craft/container APIs also reject dead
  callers for defence in depth, matching the network path?
