# OpenBlock 1.0.1 post-release audit (documentation, security, metadata, packaging)

> Status: complete · Last updated: 2026-11-25
> Scope: strict post-release audit of **documentation claims, security/privacy
> posture, release metadata and packaging** for the v1.0.0 tag. Code changes are
> out of scope for this slice; code concerns are reported, not edited.
> Depends on: [1.0.0 scope](1.0-scope.md), [1.0 acceptance](1.0-acceptance.md),
> [roadmap](00-roadmap.md), [release and operations](06-release-and-operations.md).

This report is the documentation/security/packaging half of the 1.0.1 polish
line. The client UX, server-correctness and performance agents own their own
slices; this file deliberately does not duplicate their audit sections. Findings
are recorded with severity and disposition so the release notes can link a
single page.

## Result summary

The v1.0.0 release notes and README were substantially accurate about gameplay,
protocol v2, save format 4, audio and performance. The defects were concentrated
in **release-claim drift after the last pre-release wave** and in **packaging
that was staged but described as if it were published**:

- The v1.0.0 GitHub release attached **four screenshots and nothing else** — no
  source tarball, RPM, Flatpak, container image, checksum file or SBOM — while
  the README, packaging guide and release checklist described packages as
  available.
- Several operational docs still claimed `SIGTERM` was unhandled and could lose
  a save, although `ctrlc`'s `termination` feature is enabled and both
  `SIGINT`/`SIGTERM` save. The same stale claim was repeated in the systemd
  unit, Compose file and troubleshooting page.
- The security/operator pages claimed remote IP addresses and chat were logged
  at info. The code was changed before 1.0 to log neither (Q1 fix, REQ-SEC-030);
  player names/id and a debug sender+length line are the actual behaviour.
- Spec 18 §3.13.8 still described the v1 client as current ("no survival,
  inventory, entities or title screen") next to the implemented v2 contract.
- README test/audio counts and the docs index ranges were stale; the 1.0 scope
  checkboxes still marked the delivered title/settings screens as scheduled.
- AppStream pointed at a non-installed desktop ID, had no screenshots, and the
  `.obworld` MIME association advertised an archive format the client cannot
  open. REUSE metadata missed three tracked files and gave the icon two
  licenses. CI relied on the default token permissions.

None of the findings required a game-code change. The fixes are documentation,
workflow permissions and packaging metadata; the remaining publication gaps are
listed as blockers/accepted risks below.

## Security and privacy audit

### Verified controls (no change needed)

- **No remote-IP logging or retention.** `run_accept_loop` discards the peer
  address (`Ok((stream, _addr))`) and the comment at `net.rs` cites REQ-SEC-030;
  no player/socket address is stored in `ServerPlayer`, `network_players.txt` or
  the metrics object. Join/leave logs contain the player name/id and reason.
- **No chat-content logging at info.** `handle_chat` emits only
  `chat from '<name>' (N chars)` at **debug**; `say` broadcasts without logging
  the text. This matches REQ-SEC-030 and spec 20 §7.5.
- **No secrets in the tree.** No credentials, tokens, private keys or `.env`
  secrets are tracked; `server.toml` has no secret fields; the packaged env file
  contains only `OPENBLOCK_LOG` and commented diagnostics.
- **Limits exist and are documented.** 2 MiB frame cap, 32 concurrent
  handshakes, 120 s idle timeout, 256-frame outbound queue, 30 moves/s, 20
  edits/s with 7 m reach, 5 chat lines/10 s, 16 chunk requests/s, default 8
  players, `MemoryMax=8G`/`TasksMax=4096`/`LimitNOFILE=65536`.
- **No TLS/auth is a documented design limitation, not a hidden default.** The
  README, operator handbook and security page all say loopback/LAN/VPN/SSH only
  and explain why a generic TLS proxy cannot be inserted into the JSON/TCP
  protocol.
- **CI token scope.** `permissions: contents: read` added to both workflows; no
  `pull_request_target`, no repository secrets referenced, and the only artifact
  upload is the load-gate report from `--quick`.
- **Third-party asset policy.** No Minecraft textures/sounds are bundled; the
  resource-pack loader reads user-owned local directories and the README,
  packaging guide and SECURITY policy state the legal constraint.

### Code concerns reported, not edited

1. **Healthcheck noise (AUD-028):** a `nc -z` probe opens and closes a socket
   without a protocol frame; the server logs a handshake warning/timeout every
   30 s. Consider treating a pre-handshake EOF as debug-level for loopback
   probes, or use a dedicated readiness command later.
2. **Metrics file permissions (AUD-029):** `--metrics-json` uses
   `std::fs::write`, so the file gets the process umask (0644 by default,
   0640 under the unit). Because it contains the world seed and bind address,
   creating it `0600` would be safer than relying on operator umask.
3. **All-interface default (AUD-030):** the packaged config binds
   `0.0.0.0:25565`. The firewall service is not enabled by the package, so a
   host with firewalld disabled is exposed. A loopback default (or an explicit
   install-time choice) would be safer for a no-TLS build; changing it is a
   packaging behaviour decision for 1.0.1/2.0.
4. **Client-side movement / name spoofing:** documented limitations, not
   vulnerabilities by themselves. The whitelist remains spoofable; keep the
   warning prominent.

Recorded in `packaging/README.md` § Release checklist: source tarball with

## Accepted risks (1.0.x)

- No TLS, authentication, encryption or anti-cheat; movement is
  client-authoritative and names/whitelist are spoofable. Supported deployment
  is loopback/LAN/VPN/SSH tunnel only.
- No IP/chat logging by default is intentional; operators who need abuse
  investigation must add it at the network layer or opt into debug logs with the
  documented limitations.
- No published client/server binary packages, checksums or SBOM for v1.0.0;
  users build from source. RPM/Flatpak recipes are staged and validated only by
  inspection/parsers and CI's Fedora-container checks.
- `.obworld` archive import, MIME activation, updater, mod host, telemetry,
  server browser and remote console remain post-1.0.
- Synchronous whole-world saves and the missing 4-vCPU/16/50-player capacity
  evidence remain 1.0.x gaps (owned by the performance slice).
- Windows/macOS are build/test targets with a silent audio stub, not shipped
  installers.

## Server correctness and persistence audit (1.0.1 code slice)

> Appended by the server/protocol/world/sim/content/audio correctness slice.
> The documentation/security/packaging findings above are unchanged; this
> section records defects found in the authoritative host, protocol, world save
> and simulation code, with the same severity scale.

### Scope and method

Reviewed `crates/protocol` (framing, message catalog, chunk codec, limits),
`crates/server` (handshake/accept lifecycle, tick, streaming, replication,
container windows, shutdown, host save/hash, actions, mobs, items, block
entities), `crates/world` (v4 save/migration, sections, chunk columns, light),
`crates/sim` (vitals/mobs), `crates/content` (registry/recipes/durability),
`crates/audio` (Pulse backend/threading) and `crates/core` config validation
against specs 17/18/19 and the 1.0 acceptance report. No client file was
edited. Every fixed defect below has a focused regression test; the tests use
loopback sockets, temporary worlds and fixed ticks only.

### Fixed defects

| ID | Severity | Finding | Fix / regression |
| --- | --- | --- | --- |
| SRV-001 | **High** | `Host::save` used the unchecked v4 encoder. A world whose payload exceeded the loader's 256 MiB cap (or whose file exceeded 512 MiB) was saved successfully and then refused on the next start, permanently bricking a long-running network world whose chunks are never unloaded. | `ob_world::to_bytes_checked` enforces the exact loader limits before any file is touched; `Host::save` uses it and returns a typed `PayloadTooLarge`/`SaveFileTooLarge` error while keeping the previous save. | SRV-002 | **High** | The net tick never set the core dirty flag for tick-advanced state. | SRV-003 | Medium | The 10 s handshake timeout was a per-read inactivity timeout. | SRV-009 | Medium | `ChunkColumn::set_block` updated the heightmap even for a no-op or for writing air above the top, creating a phantom surface; a same-height replacement also rescanned and discarded a valid top. ### Deferred (reported, not changed)

| ID | Severity / risk | Finding and rationale |
| --- | --- | --- |
| SRV-D01 | Medium | `registry_fingerprint` covers the block count and resource names only, not colour/opacity/fluid/hardness/tool rules/textures. A changed content pack with the same ids/names passes the v4 strict check and the network handshake. Changing the algorithm now would reject every 1.0.0 v4 save because v4 is strict; this needs a save-format version bump or dual-fingerprint migration, not a patch-release change. |
| SRV-D02 | Medium | The staged save is atomic per file but not a multi-file transaction: a crash between two renames can leave one new sidecar with the previous world. The journal in spec 17 §3.5 remains the target for the region-file save path. |
| SRV-D03 | High operational | Network mode never unloads columns. Needs save-safe unloading or the region format; operators must back up and restore/prune. |
| SRV-D04 | Medium | The outbound queue is bounded by 256 frames, not bytes; with large chunk frames a slow client can buffer hundreds of MiB before the queue disconnects it. A byte-based cap/backpressure would bound memory. |
| SRV-D05 | Low | The join burst queues one `player_state` frame per roster entry; with 256-frame queues a roster near 240+ players can spuriously fail admission. Default is 8 players and high-capacity claims are deferred, so this is documented rather than resized. |
| SRV-D06 | Low | `DedicatedServer::stop` waits 100 ms for writer threads, which are detached; a slow/full-queue client may not receive its `Disconnect` before exit (socket close is the fallback). Joining writers with a deadline is a later lifecycle change. |
| SRV-D07 | Low | The PulseAudio writer can block indefinitely in `pa_simple_write`; `AudioEngine::shutdown`/drop joins it with no timeout. A stuck server can hang process shutdown. Needs a backend timeout/abort design. |
| SRV-D08 | Low | Admission limits are global (32 handshakes) and per-connection; there is no per-IP connection/handshake bucket like the QUIC target. Loopback/LAN deployment is the documented 1.0 scope. |
| SRV-D09 | Low | The server binary accepts a world name from CLI/config without path validation (`../` or separators are operator-controlled). Client settings already reject these; server-side validation is a small follow-up. |
| SRV-D10 | Low | `Registry::from_blocks` `Box::leak`s every recipe ingredient/mob drop table, so repeated pack registry construction leaks. The base registry is built once; pack reloading is not a hot path in 1.0. |
| SRV-D11 | Low | A finite, in-range but unsafe `spawn.txt` is trusted; spawn safety is validated at creation only. Respawn revalidation is an open question in the 1.0 acceptance doc. |
| SRV-D12 | Low | `load_settings`/`load_server_config` read local operator files without a size/regular-file cap. The world directory (untrusted) is hardened; these local files are lower risk. |
| SRV-D13 | Info | Movement is client-authoritative (60 m/s horizontal bursts possible with the 2 m per-message floor), attacks use reach without line-of-sight and there is no server-side collision. Documented 1.0 limitations/anti-cheat scope. |

### Remaining risks after this slice

- The world-size save guard turns silent corruption into a loud save failure;
  operators still need an unload/region-format story before very long sessions
  reach 256 MiB of resident chunk payload (SRV-D03).
- The multi-file save group is not crash-atomic (SRV-D02), though individual
  files are now fsynced and the world commit is last.
- Registry fingerprint completeness requires a format bump (SRV-D01).
- Synchronous whole-world saves remain a tick-pause risk; this slice added
  `fsync` and more frequent autosaves, so performance numbers must be re-taken.
- No TLS/authentication/anti-cheat; movement and names remain untrusted, as
  documented for 1.0.
