> Status: complete · Last updated: 2026-11-25

This is the detailed report behind the `2026-11-25 — 1.0.1 performance/reliability
audit` entry in [Measurements](08-measurements.md). Budgets are normatively
defined in [spec/25](../spec/25-performance-budgets.md); this page records
measurements and proposals, not new targets.

## Result summary

- **No performance regression against v1.0.0.** The pristine `v1.0.0` tag was
  rebuilt in a separate worktree and re-measured. Worldgen (0.918 ms/chunk
  aggregate), host tick p99 (0.0002–0.0257 ms across phases), 289/2,025-column
  save and reload, soak, and the 8-client load gate all land inside their
  published 1.0.0 ranges and inside the budgets where 1.0.0 passed.
- **The save pause is still the material 1.0.x performance gap.** At 2,025
  columns a save takes 154–156 ms (published median 155.97 ms), five times the
  30 ms PERF-IO-004 tick-impact budget. Decomposition on this machine:
  ~55–58% zstd compression, ~39–40% serialization/allocation/CRC, <1.5% file
  write, ~1.5% fsync and directory sync. An IO thread alone cannot meet the
  budget; the encode has to leave the tick thread, or unchanged chunks have to
  be reused.
- **Autosave impact measured end to end.** With 1 Hz autosave, tick p99 is
  11.1 ms at 169 columns (vs 0.154 ms without autosave) and 85.0 ms at 1,089
  columns (max 151.3 ms), with 45 of 45 logged overruns attributed to the
  autosave tick. The 1,089-column run correctly fails the 35 ms target.
- **Reliability is mostly sound; two gaps deserve action.** 20/20
  start/stop/reload cycles, 60 s of 8-client connect/disconnect churn, a 300 s
  monitored soak, 10 SIGTERM-under-save iterations, save+stop races and
  corrupted-sidecar/world.obs cases were exercised. Sidecars recover with
  warnings; a truncated `world.obs` is detected and refused (no silent load),
  but there is no last-good fallback. `--ticks 0` is **not read-only**:
  `Host::open` streams the two-column ring and the headless path saves it, so
  reopening the same directory grows the resident set and changes the state
  hash (details below).
- **CI/benchmark lane is stable.** The four quick tools, the quick load gate
  and the backup/restore ops test ran repeatedly without a functional flake.
  CI now uploads benchmark/load-gate artifacts, has job timeouts, runs the new
  phase breakdown in the quick save benchmark, and has an opt-in manual
  reliability lane.

## The synchronous save pause (PERF-IO-004)

### Phase decomposition

`Host::save` prunes block entities, calls `ob_world::to_bytes` (serialize all
resident chunks, zstd-3 compress, CRC32C), then writes `world.obs` and eight
sidecars with temporary-file+rename. It does **not** fsync in v1.0.0 and it runs
on the network tick thread (`Core::tick` → `maybe_autosave`). The phase probe
added by `save_bench --phases` measures:

- `to_bytes` total (serialize + compress + CRC);
- pure zstd-3 compression of the decoded payload (probe);
- write+rename of the same snapshot and sidecars (no fsync);
- fsync of the snapshot and of the directory (probes only);
- residual = save total minus encode/write probes (prune, sidecar
  serialization, directory creation, scheduling).

Measured on the pristine v1.0.0 build, 5 saves per cell, medians:

| Columns | Save total | serialize+compress+CRC | of which pure compress | write+rename | fsync file+dir (probe) | residual |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 169 | 11.2 ms | 10.04 ms | 7.38 ms (66%) | 0.41 ms | 1.59 ms | 0.79 ms |
| 289 | 22.5 ms | 20.69 ms | 12.55 ms (56%) | 0.56 ms | 1.71 ms | ~0.5 ms |
| 2,025 | 163–186 ms | 162.6 ms | 92.8 ms (57%) | 1.29 ms | 2.23 ms | 7–22 ms |

The residual at 2,025 columns is noisy on the shared host; the ordering is
stable across repeats. **Compression and serialization are 95%+ of the pause;
the actual write and a durable fsync together cost only ~2–3 ms at 4.62 MiB.**
That is the key number for the design decision: moving only the write/fsync to
an IO thread leaves the 30 ms budget unmet by a wide margin.

### End-to-end autosave impact in the real server

Two controlled load-gate experiments on the pristine server, measured window
started only after every bot had its full interest set:

| Scenario | Autosave | Tick p50 | p95 | p99 | max | RSS end | Result |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | --- |
| 8 clients, radius 6 (169 cols) | off | 0.062 | 0.121 | 0.154 | 0.259 | 21.3 MiB | PASS |
| 8 clients, radius 6 | 1 Hz | 0.063 | 0.165 | **11.066** | **20.717** | 87.1 MiB | PASS, 45 saves |
| 1 client, radius 16 (1,089 cols) | off | 0.052 | 0.123 | 0.203 | 1.729 | 92.9 MiB | PASS |
| 1 client, radius 16 | 1 Hz | 0.044 | 0.131 | **85.007** | **151.289** | 125.3 MiB | **FAIL** (target 35 ms) |

The 1,089-column run logged 49 autosaves, 44 overruns above 50 ms, and 45
overrun warnings; **every one of the 45 warnings was on the line immediately
after an autosave**. That is direct attribution of the overrun to `Host::save`
rather than streaming or GC. The 169-column run stays under the 50 ms logging
threshold but still moves p99 from 0.154 ms to 11.1 ms — i.e. even a "passing"
small server spends ~1.1% of its ticks in a save pause.

At the 2,025-column reference size the dedicated server cannot load that many
columns (the network interest radius is capped at 16), so the 154–156 ms
`save_bench` measurement is the applicable number; the 1,089-column experiment
is the largest in-server demonstration.

### Durability and atomicity observations

- v1.0.0's `write_atomic` uses `std::fs::write` + `rename` with **no fsync**.
  Rename is atomic against a process crash, but not against power loss: the
  renamed file can be zero-length or stale after a crash until the kernel
  writes it back. The eight sidecars and the snapshot are also not one
  transaction: a crash between renames leaves a mixed generation.
- Truncating `world.obs` in a saved world is detected on open (exit 1); there
  is no fallback to a previous snapshot. Truncated/malformed sidecars are
  warnings and the server starts with the missing records (tested for
  `mobs.txt`, `spawn.txt`; empty `inventory.txt`/`items.txt` cases are
  inconclusive because the creative test world saved them empty).
- The 1.0.1 working tree already stages all nine files, fsyncs each temp file,
  renames them, and best-effort syncs the directory. That closes the
  power-loss durability gap but leaves the pause in place. Measured against the
  pristine v1.0.0 writer on the same machine (5 saves, one load):

| Columns / filesystem | v1.0.0 save mean | 1.0.1 WIP save mean | Delta |
| --- | ---: | ---: | ---: |
| 169 / tmpfs | 10.4–11.2 ms | 11.87 ms | +0.7–1.5 ms |
| 169 / btrfs | 11.39 ms | 21.15 ms | +9.8 ms |
| 289 / btrfs | 22.86 ms | 33.03 ms | +10.2 ms |
| 2,025 / btrfs | 156.29 ms | 171.29 ms | +15.0 ms |
| 2,025 / tmpfs | ~155 ms (published 155.97) | 162.33 ms | +6–7 ms |

  The ~10 ms btrfs delta is the nine per-file fsyncs plus staging; the extra
  2,025-column delta is the staging copy of the 155 MB snapshot. This is a good
  durability change, but it must not land as the only 1.0.1 save work: pack the
  snapshot and sidecars into one generation file (one fsync) or move the encode
  off-thread so the added durability cost is hidden. The performance lane's
  recommendation remains Option C (per-chunk cache) with the staged writer as
  its commit stage.

## Design proposal for the 1.0.x save pause

The server work is owned by the server slice; this is the performance
requirement for that work, not a patch to `crates/server`. Any accepted design
must keep the measured 2,025-column pause under 30 ms p99 end to end.

### Option A — IO thread only (insufficient)

Move write+rename+fsync to a worker. Measured cost is only 2–3 ms at 2,025
columns, but serialization+compression stays at 160+ ms on the tick thread.
This cannot meet PERF-IO-004 alone. It is useful only as the final stage of B
or C.

### Option B — snapshot copy under the lock, encode/compress off-thread

Take a consistent snapshot of the mutable world under the core mutex, then
serialize/compress/write on a save worker. Required properties:

- the copy must be a real snapshot (immutable `Arc` chunks or a deep copy);
  a borrowed `&World` cannot be encoded while the tick thread mutates it;
- a 155 MB deep copy is itself a memory copy: at ~10–20 GB/s it is ~8–16 ms,
  plus a second 155 MB allocation and page-touch cost. It fits the 30 ms
  budget only with headroom and roughly doubles transient RSS; PERF-MEM-013 is
  already marginal, so the copy must be budgeted explicitly;
- one in-flight save, latest-wins coalescing, and a bounded shutdown join;
- atomicity: a generation id (or manifest) must make the snapshot+sidecars a
  single recoverable generation; fsync file data and the directory before the
  manifest rename; keep the previous generation until the new one is durable.

This is the smallest change that can meet the budget without a format change,
but the memory copy and the extra RSS make it a stopgap.

### Option C — per-chunk/per-region precompressed cache (recommended)

Track a per-chunk revision (the world already tracks dirty sections for
meshing) and cache the compressed frame for each unchanged chunk. An autosave
then re-encodes only dirty chunks and writes a manifest plus the cached
frames. On an idle server the CPU cost drops to the manifest/CRC and a write
of ~4.6 MiB (≈1–2 ms), comfortably inside 30 ms; on a busy chunk it is bounded
by the dirty-chunk count rather than the whole world. Costs and constraints:

- format change to v5 with independently addressable frames (or region files)
  and a versioned manifest; migration from v4 is a one-time full encode;
- cache memory is the compressed size (~4.6 MiB at 2,025 columns) plus per-
  frame metadata, negligible next to 155 MB;
- consistency: dirty revisions must be captured under the same lock as the
  block mutation that bumped them; a torn revision must force a full encode;
- crash safety: write each frame/sidecar to a generation temp set, fsync,
  rename sidecars, rename the manifest last, then fsync the directory; retain
  the prior generation for recovery. This also gives a last-good fallback for
  a corrupted snapshot.

This is also the shape spec/17's region-file/IO-thread architecture points at;
it fixes the 289-column and 2,025-column rows at once and removes the
allocator churn that currently raises RSS by ~25–50 MiB after the first save.

### Short-term operator guidance

- `--save-interval 0` disables autosave but **does not remove the pause**: the
  console `save` command and the shutdown save call the same synchronous
  `Host::save`. Use it only to move the pause to a planned quiet moment or to
  trade data-loss window for latency.
- A longer interval (e.g. 300–600 s) reduces pause frequency but not duration
  and widens the loss window; do not claim zero overruns under it.
- Keep the data directory on a filesystem with cheap fsync and enough free
  space; the current writer's temp files temporarily add the full snapshot
  size, and there is no ENOSPC recovery beyond "previous file kept".
- For pre-1.0.1 builds, schedule a restart/backup rather than relying on a
  crash-consistent snapshot; v1.0.0 does not fsync.

## Open questions

1. **Save format owner:** does 1.0.x accept a v5 frame/region format, or should
   the snapshot-copy option land first? The performance lane recommends C, with
   B as a fallback if a format change is out of scope for 1.0.1.
2. **Read-only verification mode:** should `--ticks 0` stop streaming and
   saving so operators and CI can hash a snapshot without mutating it? The
   reliability harness works around this with two independent copies.
3. **Last-good fallback:** should a corrupt `world.obs` automatically fall back
   to the previous generation, and where is that generation retained?
4. **Reference hardware:** the 16/50-player `PERF-SRV` rows and a 3-run median
   on a 4 vCPU reference server remain unmeasured; this audit is a shared
   workstation.
5. **CI enforcement:** should the load-gate p99 or the save phase budget ever
   be enforced on hosted runners? Today the quick lane is advisory and the
   full gate is local/manual.
