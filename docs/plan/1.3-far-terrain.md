# 1.3 Far Terrain: Visual 8,192-Block Horizon

> Status: implemented on `v1.3-dev` · Last updated: 2026-11-25
>
> This document records the v1.3 far-terrain design, its measured cost and its
> deliberate limits. It complements [DEC-018](../decisions.md#dec-018--lod-is-visual-only-and-ships-after-10),
> [spec/03 §3.10](../spec/03-rendering.md#310-lod-frame-pacing-and-latency) and
> [spec/25](../spec/25-performance-budgets.md).

## 1. Goal

The simulated and fully meshed world stays at the existing simulation radius
(`render_distance_chunks`, 2..=32 chunks / 512 blocks). The client can now show
a **visual-only** heightfield from that near radius out to a configurable
**view distance** of 32..=512 chunks (512..8,192 blocks). The default is 128
chunks (2,048 blocks); 512 chunks is the headline maximum.

The far terrain exists to remove the old 512-block horizon wall. It must never
affect collision, streaming, spawning, drops, ore knowledge, persistence,
networking or anti-cheat, and it must not change generated world content.

FSR is being prototyped in a separate worktree and is **not** part of this
change. The far pipeline is a normal HDR scene consumer, so a later FSR
integration can run the same post chain over both paths.

## 2. UX model

`ob_core::config::Settings` gains `view_distance_chunks: i32`:

| Field | Range | Default | Meaning |
| --- | --- | --- | --- |
| `render_distance_chunks` | 2..=32 | 6 (existing) | Simulation, streaming and full-detail radius |
| `view_distance_chunks` | 32..=512 | **128** | Visual horizon including far terrain |

`Settings::clamp` clamps the view distance to `32..=512` and never lets it fall
below the simulation radius. A 1.2 config without the field loads as 128; the
new value is persisted with the rest of the settings.

The Display tab now labels `RenderDistance` **"Simulation distance"** and adds
**"View distance"** with `N chunks / 16N blocks` (for example
`512 chunks / 8192 blocks`). Changing view distance with the arrows steps 16
chunks (32 -> 48 -> ... -> 512). Crossing above 128 chunks raises one warning
toast; focusing the row always shows the GPU/visual-only note in the settings
footer. The Simulation distance row explains that streaming and simulation stay
at or below 32 chunks.

`--view-distance 32..512` is a run-only CLI override, matching the existing
`--render-distance` run-only path; editing the settings row persists normally.
`--render-distance` remains the simulation radius and is unaffected. The
`render-distance-bench` tool accepts `--view-distance N`, `--eye-height N` and
`--no-far`.

F3 reports view and simulation distances in chunks/blocks, the near full-detail
radius, and one far-terrain line: tier count, opaque quads, opaque vertices,
last build time and mesh centre, plus `rebuilding` while a worker runs.

## 3. Fast surface sampler

`Generator::height_at` and `Generator::biome_at` were already heightfield-only,
but calling both re-evaluates the shared climate fields twice. v1.3 adds:

```rust
pub struct SurfaceSample { pub height: i32, pub biome: Biome }
impl Generator {
    pub fn surface_sample(&self, x: i32, z: i32) -> SurfaceSample;
}
```

It evaluates the same `column_sample` once and returns exactly the same height
and dominant biome as `height_at`/`biome_at`. It runs no caves, features,
trees, structures or lighting. Tests compare it against both APIs on a
900+-column grid for three seeds and prove determinism and seed sensitivity.
This is the only worldgen change; generated chunk content is untouched.

## 4. Far mesh and LOD ladder

The renderer exposes a neutral `FarTerrainMesh` (world positions, linear albedo,
heightfield normal, opaque/water index buffers and bounds). The CPU builder is
`ob_render::far_terrain::build_far_terrain(seed, config, sampler, center)`; the
client supplies `surface_sample` through a `FarBiome` mapping, so the render
crate never depends on worldgen types. Tools and screenshots use the same
builder.

The mesh is a hierarchy of concentric square-annulus tiers on world-aligned
lattices. `inner` is the simulation radius minus the 96-block recenter
hysteresis, and `outer` is the view radius plus the hysteresis:

| Tier | Nominal radius (blocks) | Cell (blocks) | Purpose |
| ---: | --- | ---: | --- |
| 0 | inner .. 512 | 8 | Overlap the streamed near world |
| 1 | 512 .. 1,024 | 16 | Near horizon |
| 2 | 1,024 .. 2,048 | 32 | Mid distance |
| 3 | 2,048 .. 4,096 | 64 | Far hills |
| 4 | 4,096 .. outer | 128 | Final fogged horizon |

Each tier is sampled 1.5 cells past its nominal bounds, so adjacent tiers
overlap instead of meeting at a T-junction. Farther tiers are 0.15 blocks lower
per tier (plus a 0.65-block base offset) so the finer tier wins the depth test in
the overlap; the near world always owns the volume inside `inner`. There are no
cracks or holes at a tier boundary by construction.

At the 512-chunk maximum with a 32-chunk simulation radius:

| Metric | Value |
| --- | ---: |
| Tiers | 5 |
| Opaque quads | 47,950 |
| Opaque vertices | 49,950 |
| Opaque triangles | 95,900 |
| Water triangles | 11,581 |
| CPU/GPU vertex + index data | ~3.8 MiB |
| Build time (release, quiet box) | 8.0–8.4 ms |

The default 128-chunk view with the default 6-chunk simulation radius builds
about 35.5k quads (~71k triangles, four tiers). Memory is bounded: vertices are 36 bytes
and indices are 32-bit; the whole 512-chunk far scene is under 5 MiB.

### 4.1 Per-vertex appearance

Each vertex stores a world position, linear RGB albedo and a unit heightfield
normal. The CPU bakes:

* biome surface rules: grass/forest floor, desert sand, snowy-taiga snow,
  mountain stone/snow, beaches and a sand/gravel/clay seabed;
* slope thresholding (grass/forest/snow -> stone on steep ground);
* curvature shading from the normal, a per-vertex hash variation and a broad
  sine field so large low-poly faces do not read as flat colour;
* subtle water depth colour from shallow turquoise to deep blue.

Water is a separate index list clipped to the sea plane with a
Sutherland-Hodgman pass per cell, giving a smooth shoreline instead of a
stair-stepped cell boundary. The far water mesh is drawn before the sorted near
water in the existing translucent pass. It is visual-only and has no
collision, flow or gameplay authority.

## 5. Determinism and recentering

The mesh is a pure function of the world seed, configuration and centre. The
same inputs produce byte-identical vertices and indices (tested). It is fixed
world-space geometry; the client does not slide it per frame.

The client keeps at most one rebuild in flight on a named `ob-far-terrain`
thread. A rebuild starts when:

* the configuration or world seed changes; or
* the camera moves more than 96 blocks from the mesh centre.

Starts are throttled to at most one per 350 ms. A completed build that is
already more than 1.5 x the hysteresis away from the latest camera position is
discarded rather than uploaded (teleport/fast-flight guard). The upload happens
on the main thread only after the worker finishes; sampling and meshing never run
on the frame thread. The outer radius includes the hysteresis, so the horizon
stays covered while a build is pending.

## 6. Render integration

* New `far_terrain` pass and WGSL shader in `ob_render`; no changes to mesh
  formats, bind-group layouts or shadow resources.
* Opaque far terrain draws after near full sections and far batches, depth
  tested and depth-writing, with no culling beyond one frustum + distance AABB
  test. It is drawn **before** entities/dropped items.
* Far terrain casts no sun shadows and is excluded from all shadow cascades.
  It receives a cheap directional/ambient shade using the same sun direction,
  world-light tint and day/night clock as the near world.
* Far water draws in the existing water pass with alpha blending, before the
  near water. There is exactly one far-water draw.
* Fog uses the shared `Camera.fog` range. Long horizons (>1,000-block far plane)
  start at 12% of the far plane and reach the horizon colour at 95%; at 8,320
  blocks that is 998..7,904 blocks. The near world uses the same range, so the
  512-block seam cannot show more or less haze than the far mesh. Shorter
  configurations keep the 1.1 fog behaviour.
* Camera far plane: `far_plane_for_view_distance(chunks) = 16 x chunks + 128`
  (8,320 at 512 chunks). The simulation radius still uses the old
  `16 x chunks + 48` helper.
* `Renderer` and `OffscreenRenderer` both expose
  `set_far_terrain`/`clear_far_terrain`/`far_terrain_bounds`; screenshots, F2,
  the main `--screenshot` modes and the benchmark upload the same mesh. The
  windowed App and NetApp rebuild it in a worker.

`RenderStats` adds far opaque/water draw, vertex and triangle counters. The far
pass adds at most two draw calls (one opaque, one water).

## 7. Multiplayer seed and authority

The protocol handshake already carries the world seed in `ServerInfo`; the
network client reads `client.server_info().seed` and builds the visual mesh from
that seed. No protocol change is needed. While connecting, disconnected or in a
menu without a server, the far mesh is cleared rather than guessed.

Multiplayer far terrain is visual-only in exactly the single-player sense: it
is not streamed, simulated or authoritative, and the server's interest radius
stays at the simulation distance (<=32 chunks). A server may therefore send no
columns beyond 512 blocks while the client still draws its own heightfield.
A seed or content mismatch can only change pixels, never state.

## 8. Measurements

See [08-measurements §v1.3 far terrain](08-measurements.md#2026-11-25--v13-far-terrain-512-chunks).
The short version at the 512-chunk setting with `High`, 8,192-block view,
4,225 columns, 2,620 near sections + 1,010 far batches, 120 measured frames and
the same binary with `--no-far` as the paired control:

| Run | p50 ms | p95 ms | p99 ms | p50 FPS | p95 FPS |
| --- | ---: | ---: | ---: | ---: | ---: |
| 1280x720 no far terrain | 10.59 | 10.72 | 10.82 | 94.4 | 93.3 |
| **1280x720 far terrain** | **11.19** | **11.31** | **11.33** | **89.3** | **88.4** |
| 1920x1080 no far terrain | 14.85 | 15.04 | 15.93 | 67.1 | 66.5 |
| **1920x1080 far terrain** | **15.70** | **15.80** | **15.87** | **63.7** | **63.3** |

Far terrain adds **0.60 ms** at 720p and **0.85 ms** at 1080p (5.7% of frame
time in both cases). The target — 60 FPS at 1080p High with a 512-chunk visual
distance — is met at p50 (63.7) and p95 (63.3). RSS after build was 269–271 MiB,
peak 273–279 MiB, far mesh data 3.8 MiB (the 1.2 near-world scene is ~270 MiB
RSS and ~1.49 GiB of cached near vertex data).

An earlier set of runs was taken while another windowed OpenBlock process was
using the same integrated GPU; those contended numbers (19.5 FPS near-only) are
not used for the target claim and remain in the commit discussion only.

## 9. Tests

* Settings: 1.2 configs load with the 128 default; clamp 32..512 and
  view >= simulation; Display row text, stepping and the one-time >128 warning.
* Sampler: exact height/biome match, determinism, seed sensitivity.
* Mesh: tier coverage/overlap, 512-chunk quad budget, determinism, water
  coverage/shore clipping, finite normals/colours, no-gap overlap.
* GPU: offscreen far pipeline draws one opaque pass, writes HDR colour/depth,
  clears without one, and creates no wgpu validation errors; far water pipeline
  and both windowed/offscreen APIs share the same scene renderer.
* F3: view/sim/near-full far line, compact line, and the overlay layout fits
  1280x720 and 960x540 at every GUI scale.
* Existing render, client, tool and GPU suites stay green.

## 10. Limitations

* **Style seam at the simulation radius.** Geometry, colours and depth agree
  and there are no holes, but the near world is textured block geometry and the
  far mesh is a smooth heightfield. From a high flying viewpoint the 512-block
  boundary is visible as a change in detail. No dither/cross-fade is used.
* **Coarse water and coastlines.** Water is clipped to the sea plane per tier
  cell; at 4-8 km the coastline follows the 64-128 m cell spacing and lake
  shapes are approximate. Water alpha is uniform; there is no flow, foam or
  reflection beyond a cheap sky tint and sun highlight.
* **No trees, structures or caves.** The far mesh is the terrain heightfield.
  Forests remain visually represented only by surface colour, as intended.
* **Rebuild hitch risk.** Sampling/meshing is off-thread and upload is one
  buffer write, but a very large 512-chunk rebuild allocates ~5 MiB and can
  still cost a few milliseconds on the main thread. Rebuilds are hysteretic and
  throttled; fast travel can discard a stale result.
* **Depth precision.** The far plane grows to 8,320 blocks with a 0.05 near
  plane. The near/far overlap is only at 512-520 blocks (0.31 m quantum), so the
  overlap is offset, and the far heightfield has no coplanar second surface.
  Reverse-Z remains post-1.3 work.
* **Seed/version mismatch in multiplayer.** The handshake seed is sufficient
  for vanilla content. A server with a different content pack or generator
  version can draw a different far silhouette; it remains visual-only.
* **FSR is not integrated here.** The other worktree owns that experiment; this
  pass renders into the existing HDR target and post chain.
* **Far terrain is measured through the offscreen readback harness**, which
  includes a blocking GPU→CPU copy and is not a windowed present-to-present
  measurement. The 63.7/63.3 FPS result is a p50/p95 result from that harness.
